# Verification report

Evidence base for `docs/spec.md`. Produced by an 11-agent verification pass before implementation
began: 7 agents fact-checking design assumptions against primary sources, then 4 adversarial
critics reviewing the design given those findings.

Method: library source code was read directly, `genanki` and the official `anki` package were
installed and exercised, generated `.apkg` files were round-tripped through a real Anki 26.08
collection, LibreOffice concurrency was measured in Docker, and Anthropic/Fly/Anki documentation
was read at source. Blog posts and training priors were not treated as evidence.

Result: 41 claims CONFIRMED, 8 REFUTED, 13 PARTLY_TRUE; 17 blocker-severity design issues.

Caveat on the critique: the design brief given to the four critics omitted the agreed card
review/edit step. Issues premised on "the user never sees the cards" are therefore partly
answered by the design as specified.

# Verification distillate
## Findings that are NOT clean CONFIRMED

### genanki
**[REFUTED]** The '::' nesting is something genanki does.

- evidence: '::' appears nowhere in genanki. `Deck.to_json()` writes `"name": self.name` as an opaque string. The nesting is entirely Anki-side: `NativeDeckName::from_human_name` converts '::' to the internal \x1f separator (rslib/src/decks/name.rs), and `match_or_create_parents` in rslib/src/decks/addupdate.rs explicitly 'If parent deck(s) exist, rewrite name to match their case. If they don't exist, create them.' Anki's importer matches decks by NAME, not by deck_id (`get_deck_by_name` in apkg/import/decks.rs).
- source: https://raw.githubusercontent.com/ankitects/anki/main/rslib/src/decks/addupdate.rs + rslib/src/decks/name.rs
- IMPACT: You do NOT need to emit parent decks — emit one Deck per full leaf path only. But because Anki matches decks by name, deck_id is near-irrelevant for placement while still having to be unique and valid (see deck_id findings).
**[REFUTED]** genanki 0.13.1 handles Cloze notes correctly.

- evidence: Released 0.13.1 contains a real bug in `Note._cloze_cards()`: `if card_ords == {}: card_ords = {0}`. `{}` is an empty DICT, so this comparison against a SET is ALWAYS False. A cloze note whose Text field contains no `{{cN::}}` marker therefore yields ZERO cards. Verified empirically: note with fields ['No cloze markers at all here.',''] produced `cards=[]`, and after import into Anki the note EXISTS in the collection with 0 cards attached — silent card loss, no error, no warning. This is fixed on GitHub main (`if not card_ords:`) by commit 'Fix comparison between set and dictionary (#146)' dated 2024-11-12, but 0.13.1 was released 2023-11-12 and NO release has shipped since, so the fix is unreleased.
- source: genanki/note.py (0.13.1) vs https://raw.githubusercontent.com/kerrickstaley/genanki/main/genanki/note.py line 104
- IMPACT: Claude WILL occasionally emit a cloze card with missing/malformed markers. Validate server-side with `re.search(r'\{\{c\d+::', text)` before constructing the Note; if it fails, downgrade the card to BASIC_MODEL rather than passing it to CLOZE_MODEL. Do not rely on genanki to catch this.
**[PARTLY_TRUE]** genanki is actively maintained and safe to depend on.

- evidence: Repo kerrickstaley/genanki is NOT archived and has 2660 stars, but: last commit to main is 2024-12-30 (~20 months stale as of 2026-08); last PyPI release 0.13.1 is 2023-11-12 (~2.7 years old); 30 open issues and 6 open PRs. Open issue #155 is literally titled 'Please Release a New Version' (2025-03-14). Open issue #159 '[FEATURE REQUEST] Add support for Collection Schema v18' and #100 'Support new Anki package format' confirm genanki still emits only the legacy format. However, I found NO breakage against current Anki: a genanki-built package imported cleanly into a real anki==26.08 collection (latest release, published 2026-08-01).
- source: https://api.github.com/repos/kerrickstaley/genanki + PyPI JSON + live import test
- IMPACT: Acceptable to depend on, but pin exactly and vendor-patch the empty-cloze bug rather than waiting for a release. Budget for the possibility that genanki never ships another version; the surface you use is small enough (~4 classes) to fork if needed.
**[REFUTED]** Update-in-place works regardless of what pass 2 regenerates for a given card UUID.

- evidence: It silently fails if the NOTETYPE changes for an existing GUID. `maybe_update_existing_note`: `if !self.merge_notetypes && incoming.notetype_id != existing.notetype_id { self.imports.log_conflicting(incoming); }` — the note is logged as 'conflicting' and NOT updated at all. Verified twice: (a) same GUID flipped Basic->Cloze gave new=0 upd=0 dup=0 CONFLICT=1 with fields left at their OLD values; (b) same GUID, same field layout, but a DIFFERENT model_id (simulating a per-job randomised model id) also gave CONFLICT=1, left the note stale, AND created a duplicate notetype renamed 'AI-Anki Basic+'. Using the same model_id gave a clean updated=1. merge_notetypes defaults to false, and even with it true, `existing.is_cloze() != incoming.is_cloze()` raises NotetypeKindMergeConflict.
- source: rslib/src/import_export/package/apkg/import/notes.rs `maybe_update_existing_note` + live tests
- IMPACT: Two hard requirements. (1) Model IDs must be fixed app-wide constants — never `random.randrange(1<<30, 1<<31)` per job as genanki's README suggests. Use genanki.BASIC_MODEL/CLOZE_MODEL, or your own two hardcoded ints, and treat them as a migration-worthy schema. (2) Persist the chosen note type alongside the card UUID in SQLite and PIN it across regenerations. If pass 2 wants to change a card from Basic to Cloze, you must mint a NEW UUID and retire the old one, otherwise the change silently no-ops.
**[PARTLY_TRUE]** Image Occlusion cards can be produced with genanki in a later phase.

- evidence: genanki has NO built-in Image Occlusion support — open feature request #149 '[FEATURE REQUEST] Support for Image Occlusion Enhanced' (2024-11-21) is unresolved, and no IO model exists in builtin_models.py. However, modern Anki ships a native 'Image Occlusion' notetype: it appeared in the default notetype list of the fresh anki==26.08 collection I created ('Basic', 'Basic (and reversed card)', 'Basic (optional reversed card)', 'Basic (type in the answer)', 'Cloze', 'Image Occlusion'). So the target exists; genanki simply cannot emit it out of the box — you would hand-construct a `genanki.Model` mirroring Anki's IO notetype schema and field encoding.
- source: https://api.github.com/repos/kerrickstaley/genanki (issue #149) + notetype list from a fresh anki 26.08 collection
- IMPACT: Keep Image Occlusion firmly in a later phase and treat it as genuine R&D, not a genanki feature toggle. You must reverse-engineer Anki's IO notetype id, field layout and occlusion-shape serialisation, and match the built-in notetype id exactly or every IO import will hit the notetype-conflict skip path.

### anki-import
**[PARTLY_TRUE]** Is there an import option/dialog the user must choose correctly for update-in-place, or is it automatic?

- evidence: There IS a dialog (Anki 23.10+ import screen), but the defaults are already correct for update-in-place — no user action is needed in the normal case. Defaults, from ImportAnkiPackagePage.svelte and rslib service.rs `get_import_anki_package_presets` (whose unit test asserts the fresh-collection values): 'Import any learning progress' (with_scheduling) = OFF; 'Import any deck presets' (with_deck_configs) = OFF; then a COLLAPSED <details> disclosure labelled 'Updates' containing 'Merge note types' (merge_notetypes) = OFF, 'Update notes' = If newer, 'Update note types' = If newer. The update_notes/update_notetypes enum is the proto `ImportAnkiPackageUpdateCondition` with IF_NEWER = 0, so prost's Default is If newer; options are exactly If newer / Always / Never. Values are sticky — they are written back into collection config on every import (`col.set_config(ConfigKey::UpdateNotes, ...)`), so a user who once set 'Never' keeps it. Crucially, 'Import any learning progress' being OFF does NOT harm existing scheduling: it only strips scheduling from the INCOMING cards, and existing cards are never rewritten either way (verified with with_scheduling=True and False — existing ivl=30/reps=9 unchanged in both).
- source: https://raw.githubusercontent.com/ankitects/anki/main/ts/routes/import-anki-package/ImportAnkiPackagePage.svelte ; .../choices.ts ; https://raw.githubusercontent.com/ankitects/anki/main/rslib/src/import_export/service.rs ; https://raw.githubusercontent.com/ankitects/anki/main/ftl/core/importing.ftl ; local exp2.py case F
- IMPACT: Low, but the app's download page should tell users: just click Import, leave the defaults alone. If a schema change ever ships, users would additionally have to expand 'Updates' and enable 'Merge note types' — another reason to freeze the models (see finding 3).

### image-occlusion
**[REFUTED]** Image Occlusion requires shipping a CUSTOM note type (the design's assumption).

- evidence: Anki ships a stock, built-in Image Occlusion notetype since 23.10. Manual: "Anki 23.10+ supports Image Occlusion cards natively." 23.10 release notes: "Anki now has built-in support for creating image occlusions. Select the automatically-added 'Image Occlusion' notetype in the add screen to use it." Verified empirically: opening a brand-new collection with the official `anki` 26.8 Python package lists 6 stock notetypes, the 6th being ('Image Occlusion', originalStockKind=6). The stock kind enum is `StockNotetype.OriginalStockKind.ORIGINAL_STOCK_KIND_IMAGE_OCCLUSION = 6` (proto/anki/notetypes.proto). Anki identifies an IO notetype ONLY by `original_stock_kind == 6`, never by name — see `get_first_io_notetype()` in rslib/src/image_occlusion/notetype.rs. So you do not invent a note type; you replicate the stock one (or a renamed clone of it) with originalStockKind=6.
- source: https://docs.ankiweb.net/editing.html#image-occlusion ; https://changes.ankiweb.net/changes/23.10.html ; https://raw.githubusercontent.com/ankitects/anki/main/rslib/src/image_occlusion/notetype.rs ; local: /private/tmp/claude-501/-Users-hairymammoth-Documents-ai-anki/1c92016b-847c-4e4c-baea-601337c361e9/scratchpad/io_dump.py
- IMPACT: Image Occlusion drops from "design and ship a bespoke note type + JS masking renderer" to "emit the stock notetype JSON + a text field of cloze-wrapped shape strings". The card-rendering JS (`anki.imageOcclusion.setup()`) is supplied by the Anki client, not by us. Phase-later status is a scheduling choice, not a complexity necessity.
**[PARTLY_TRUE]** genanki can produce notes of the built-in Image Occlusion type in an .apkg.

- evidence: Not out of the box, but with a ~10-line subclass — and I proved it end to end. genanki 0.13.1's Model.to_json (site-packages/genanki/model.py:108) emits a fixed dict with no `originalStockKind` and no per-field `tag`/`preventDeletion`. However Anki's schema-11 JSON deserializer DOES accept both: `original_stock_kind: i32` with `#[serde(rename_all = "camelCase")]` on NotetypeSchema11, and `tag: Option<u32>` / `prevent_deletion` on NoteFieldSchema11 (rslib/src/notetype/schema11.rs; both names are in RESERVED_NOTETYPE_KEYS / RESERVED_FIELD_KEYS). Result: notetype imported with originalStockKind=6; 3 cards generated from c1/c2/c3 (genanki's cloze regex `{{c(\d+)::.+?}}` matches image-occlusion clozes); `col.get_image_occlusion_note(nid)` parsed the shapes back into proto (rect/ellipse/polygon with all properties incl. oi); and `card.question()` rendered `<div class="cloze" data-ordinal="1" data-shape="rect" data-left=".2325" data-top=".3261" data-width=".202" data-height=".0975">`. genanki upstream has no built-in support and is semi-dormant: last release 0.13.1 (2023-11-12), last repo push 2024-12-30, and the only occlusion issue is #149 "[FEATURE REQUEST] Support for Image Occlusion Enhanced" (open, and about the old add-on, not the built-in type). Community precedent for the native format exists outside Python, e.g. 2anki.net PR #2190 "feat: image occlusion — batch canvas editor with native Anki 23.10 IO format".
- source: /private/tmp/claude-501/.../scratchpad/io_roundtrip.py (verified live); genanki/model.py:108-125; https://raw.githubusercontent.com/ankitects/anki/main/rslib/src/notetype/schema11.rs ; https://github.com/kerrickstaley/genanki/issues/149
- IMPACT: Keep genanki. Add a small `RawModel(genanki.Model)` subclass that overrides to_json to set d["originalStockKind"]=6 and per-field tag/preventDeletion. Copy the stock qfmt/afmt/css verbatim into a constant (they are stable and short). Image goes in Package.media_files. Budget: roughly a day, not a phase.
**[PARTLY_TRUE]** The official `anki` PyPI package is a viable alternative to genanki for building .apkg files for the whole project.

- evidence: Technically excellent, legally and operationally risky. Technically: anki 26.8, requires_python >=3.10, deps decorator/distro/markdown/orjson/protobuf(>=6,<8)/requests/typing-extensions. I built a full deck with it (anki_build.py): `col.decks.id("AI Anki::Biology::Cell Structure")` auto-creates the parent subdecks; `note.guid = "my-stable-uuid"` is directly settable and survives export/import; the built-in IO notetype is used with ZERO hacks (`col.models.all()` → originalStockKind==6, set Occlusion/Image/Header, 2 cards generated); `col.media.add_file()` handles media; `col.export_anki_package(out_path=..., options=ExportAnkiPackageOptions(with_scheduling=..., with_media=True, legacy=False), limit=None)` writes a modern v3 .apkg in 0.28s; collection open took 0.056s. BUT: (a) LICENSE is AGPL-3.0-or-later (genanki is MIT). Linking an AGPL library into a publicly-reachable web service triggers the network-use clause — you must offer the complete corresponding source of ai-anki to its users. (b) Binary-only distribution: 6 wheels, all cp310-abi3, NO sdist. Linux tags are manylinux_2_35 (glibc >= 2.35) x86_64 + aarch64 — fine on debian bookworm/python:3.12-slim (glibc 2.36), fine on Fly.io arm, but IMPOSSIBLE on Alpine/musl and on debian bullseye (glibc 2.31). (e) It is stateful: you build a real SQLite collection on disk and export it, so each job needs a temp collection directory and cleanup, unlike genanki's stateless write.
- source: https://pypi.org/pypi/anki/json ; https://github.com/ankitects/anki/blob/main/LICENSE (AGPL-3.0-or-later, per the PyPI long description) ; local: /private/tmp/claude-501/.../scratchpad/anki_build.py
- IMPACT: Do NOT swap the project onto `anki` just for occlusion — the AGPL network-copyleft obligation on a publicly deployed service is a much bigger commitment than a 10-line genanki subclass. Keep genanki (MIT) as the emitter. Optionally add `anki` as a DEV-ONLY test dependency (never imported by the server) to assert in CI that generated .apkg files import cleanly, generate the right cards, and render the right HTML — that is exactly what I did here, and it is high-value regression cover. If you ever do adopt `anki` at runtime, pin the exact version, pin a glibc>=2.35 base image, and plan to publish the source.
**[PARTLY_TRUE]** A vision model can return usable bounding boxes for labels on a diagram, and the coordinate space converts cleanly into Anki's format.

- evidence: Anthropic ships a dedicated guide for exactly this. Key constraints, quoted: "Claude works best with absolute pixel coordinates. Ask for them explicitly in your prompt... Claude does not work well when you ask for normalized coordinates, for example: 'Return bounding box coordinates between 0 and 1000.' Always ask for pixel coordinates and normalize in your own code if you need to." Origin is top-left, x right, y down — the same convention Anki uses. Accuracy is explicitly hedged: the Vision limitations page says "Claude's coordinate and localization outputs are approximate", and the coordinates guide says "Coordinate accuracy is best when you state the expected coordinate format in your prompt and spot-check results visually before processing at scale. Small elements lose precision when an image is downscaled: for fine targets, crop the region of interest and send the crop (offset returned coordinates by the crop origin), or use a high-resolution-tier model." Coordinates are in the image AFTER Claude's server-side resize; the resize rule is largest aspect-preserving size satisfying both an edge limit and a visual-token limit of ceil(w/28)*ceil(h/28) — 2576 px / 4784 tokens on the high-resolution tier (Claude 4.7 and later, which includes claude-opus-5), 1568 px / 1568 tokens otherwise. Anthropic publishes a `resized_size()` reference implementation. Also: "Claude then pads every image... up to the next multiple of 28 pixels on the bottom and right edges... Always normalize or rescale by the resized dimensions, not the padded dimensions." CRITICAL for this project: "For PDF support, pages are rasterized to images server-side at dimensions you don't control, so the returned coordinates can't be reliably mapped back onto the page. To work with coordinates on PDF content, rasterize the pages to images yourself and use the pre-resize approach."
- source: https://platform.claude.com/docs/en/build-with-claude/vision-coordinates ; https://platform.claude.com/docs/en/build-with-claude/vision#limitations
- IMPACT: Three concrete design changes for the occlusion phase. (1) The agreed ingestion path — PDFs sent to Claude as native document blocks — CANNOT produce usable occlusion coordinates. Occlusion needs its own sub-pipeline: locally rasterize the specific diagram page (pypdfium2/PyMuPDF), optionally crop the figure, pre-resize with Anthropic's resized_size() for the high-res tier (2576/4784), send it as an IMAGE block, and store that same rasterized PNG as the Anki media file so the mask geometry matches the picture the user sees. (2) Prompt for absolute pixel [x1,y1,x2,y2] via structured outputs, then divide by the pre-resized dimensions yourself to get Anki's 0–1 fractions — never ask Claude for normalized coords. (3) Because boxes are approximate, the UI must let the user drag/resize masks before download, or accept that some masks will be visibly off. Anki's own editor is the fallback: since the note is a genuine stock IO note, the user can open it in Anki and nudge the shapes.

### anthropic-docs
**[REFUTED]** Using the Files API (upload once, reference by file_id) RAISES the PDF page-count and size limits versus inlining base64.

- evidence: The Files API only sidesteps the 32 MB *request* limit; it does not raise the page limit or the context window. pdf-support.md: "For large PDFs, consider uploading with the Files API and referencing by `file_id` to keep request payloads small." And explicitly: "Requests with large PDFs can also fail before reaching the page limit, even when using the Files API." vision.md repeats it: "Even when using the Files API, requests with many large images can fail before reaching the 600-image count." The Files API's own limits are 500 MB per file and 500 GB total per organization (note: 500 GB, not the 100 GB figure in stale sources), file ops are free, ~100 req/min during beta, files persist until deleted, beta header `files-api-2025-04-14` required on both upload and any Messages request that references the file.
- source: https://platform.claude.com/docs/en/build-with-claude/files.md
- IMPACT: Files API is still the right call for the 150 MB/job cap — it is the ONLY way to exceed 32 MB of source material in one request. But it must not be treated as raising the real ceiling, which is the 1M context window (see gotchas). Job caps must be enforced against a token estimate from `count_tokens`, not against page count or MB.
**[PARTLY_TRUE]** Structured outputs are compatible with PDF document blocks AND with citations.

- evidence: Compatible with PDF document blocks: yes — no restriction appears anywhere in structured-outputs.md or pdf-support.md, and citations is named as the sole incompatibility. NOT compatible with citations: citations.md states it in a dedicated callout — "Citations and structured outputs are incompatible. Citations cannot be used together with structured outputs. If you enable citations on any user-provided document (`document` blocks or `search_result` blocks) and also include the `output_config.format` parameter (or the deprecated `output_format` parameter), the API returns a 400 error. This is because citations require interleaving citation blocks with text output, which is incompatible with the strict JSON schema constraints of structured outputs." Separately, citations on scanned PDFs do not work at all: "As image citations are not yet supported, PDFs that are scans of documents and do not contain extractable text are not citable."
- source: https://platform.claude.com/docs/en/build-with-claude/citations.md
- IMPACT: The design's per-card `source page` tag cannot come from the citations API if pass 2 uses structured outputs — that combination is a hard 400. Either (a) drop citations and have the model emit a `source_page` integer field inside the JSON schema (self-reported, unverified), or (b) drop structured outputs on pass 2 and use citations + a `strict: true` tool call instead. Option (a) is simpler and is what the design implicitly assumes; just do not expect verified page provenance. Also: scanned PDFs are uncitable regardless, so (b) would silently degrade for exactly the scanned-lecture-notes case.
**[PARTLY_TRUE]** A large nested hierarchical "deck plan" schema will work with structured outputs.

- evidence: structured-outputs.md §JSON Schema limitations. NOT supported: "Recursive schemas"; "Complex types within enums"; external `$ref`; numerical constraints (`minimum`, `maximum`, `multipleOf`); string constraints (`minLength`, `maxLength`); "Array constraints beyond `minItems` of 0 or 1" (so `maxItems` is unsupported); `additionalProperties` set to anything other than `false`; `allOf` with `$ref`. Supported: all basic types, `enum` (primitives only), `const`, `anyOf`/`allOf`, `$ref`/`$defs`/`definitions` (internal), `default`, `required`, `additionalProperties:false` (must be explicitly false on every object), the listed string formats, `minItems` of 0 or 1, and a limited regex subset for `pattern` (no backreferences, lookahead/lookbehind, `\b`, or large `{n,m}` ranges). Unsupported features return a 400 with details. No documented hard limit on nesting depth or property count. Two further behaviors that bite: property ordering is reordered so that **required properties appear first, then optional**; and `enum`/`const` string capitalization is not guaranteed ("Claude may return a value that differs from your schema only in capitalization, typically in the first letter of a word following a space").
- source: https://platform.claude.com/docs/en/build-with-claude/structured-outputs.md
- IMPACT: Two concrete changes. (1) The topic tree MUST NOT be recursive. Model it as a flat array of topics each carrying a `path` string ("Cardiology::Arrhythmias::AF") or a fixed-depth nesting (topic -> subtopic -> subsubtopic, spelled out), not a self-referencing `Topic` node. Pydantic models that self-reference will emit a recursive `$ref` and 400. (2) `proposed_card_count` cannot be bounded with `minimum`/`maximum` and the topics array cannot be bounded with `maxItems` — enforce those in Python after parsing, and put the intent in the field `description` (the Python SDK auto-strips unsupported constraints and folds them into descriptions, so a Pydantic `Field(ge=1, le=30)` will silently become advisory, not enforced). Also set `additionalProperties: false` on every object, and compare `note_type`/`difficulty` enum values case-insensitively.

### prompt-caching
**[PARTLY_TRUE]** A cache entry written by a pass-1 request can be READ by a pass-2 request that has a different instruction suffix — i.e. the two-pass design shares one cached document.

- evidence: The mechanism supports it: the cache key is "a cryptographic hash of the prompts up to the cache control point," and "only requests with identical prompts can access a specific cache" — identical UP TO the breakpoint. Different suffixes after the breakpoint are irrelevant to the key. Docs explicitly endorse this shape: "For a prompt with a varying suffix (timestamps, per-request context, the incoming message), place the breakpoint at the end of the static prefix, not on the varying block." BUT this holds ONLY if everything before and including the breakpoint is byte-identical. The render order tools → system → messages means a per-pass system prompt breaks it: if pass 1's system says "produce a deck plan" and pass 2's says "produce cards for topic X," the system tier differs, so the messages tier (where the document lives) can never match, and every pass-2 call pays full price.
- source: https://platform.claude.com/docs/en/build-with-claude/prompt-caching.md (privacy FAQ; Key takeaway on breakpoint placement; Structuring your prompt)
- IMPACT: The design works but must be restructured to guarantee it. Required layout, identical in BOTH passes: [tools: identical or absent] → [system: ONE generic, pass-agnostic system prompt, byte-identical across both passes] → [messages[0].content: document block(s), with cache_control {type: ephemeral, ttl: 1h} on the LAST document block] → [then, in the same user message AFTER the breakpoint, the pass-specific instruction text: "produce a deck plan" vs "produce cards for topic X"]. Do NOT put the pass-specific instruction in `system`. Also keep effort, thinking config, tool_choice, and the tools array identical across passes. If you get this right, pass 1 pays the 1h write and every pass-2 topic call pays 0.1x.

### libreoffice
**[PARTLY_TRUE]** LibreOffice needs a writable HOME / user profile dir and *silently fails or hangs* without one.

- evidence: The requirement is real, but the failure is neither silent nor a hang — it is fast and loud. Running as uid 65534 with HOME=/nonexistent and no `-env:UserInstallation`:

  exit=77, elapsed=0s, 0 PDFs
  "LibreOffice 7.4 - Fatal Error: The application cannot be started. User installation could not be completed."

The fix is confirmed: adding `-env:UserInstallation=file:///tmp/<dir>` makes it succeed (exit=0, 1 PDF, 3s) even with HOME still pointing at /nonexistent. It also works with `--read-only` rootfs plus a tmpfs on /tmp — I verified a full PPTX->PDF conversion under `docker run --read-only --tmpfs /tmp -u 65534:65534 -e HOME=/nonexistent`. I could not reproduce a hang in any HOME/profile configuration; I also injected a stale `.lock` file into an existing profile and the next run recovered cleanly (exit 0, 1s). The genuinely silent failure mode in this system is the concurrency one (see next finding), not the HOME one.
- source: Local Docker experiments; container exit code 77 and stderr captured directly
- IMPACT: Do not build hang-detection logic specifically around the HOME problem — it fails fast with a distinctive exit code 77 and a clear message. Still always pass `-env:UserInstallation` (it is required for concurrency anyway). Keep a subprocess timeout for other reasons, but do not expect HOME misconfiguration to manifest as a hang.
**[REFUTED]** Concurrent conversions in one container are safe, or LibreOffice serialises on a shared user profile.

- evidence: LibreOffice does NOT serialise on a shared profile — it FAILS, and does so silently. Six concurrent conversions of the same DOCX in one container sharing the default profile (HOME=/root, no `-env`):

  wall=7288ms, only 2 of 6 PDFs produced; jobs 1,4,5,6 exited 1
  Full stdout/stderr of every failed job: ONLY "Warning: failed to launch javaldx" — no error, no lock message, no diagnostic whatsoever.

Repeated to confirm: 2 of 6 succeeded, 4 exited 1 with zero explanatory output. A two-job test sharing one explicit `-env:UserInstallation` dir reproduced it (A ok, B exit 1, no message).

With a separate `-env:UserInstallation` temp dir per invocation: 6/6 succeeded, and it is genuinely parallel, not serialised. Scaling on 4 CPUs with an image-heavy 40-slide PPTX (3028ms single): N=1 3028ms, N=2 3033ms, N=4 3272ms, N=6 5688ms, N=8 9901ms — all 100% success. So throughput scales with CPU count up to nproc.

Critically, on 1 vCPU there is NO concurrency benefit at all: N=1 2922ms, N=2 5901ms, N=4 12280ms — perfectly linear. Peak RSS measured at ~218 MB for one conversion.

Correct pattern: one fresh temp profile per invocation (`tempfile.TemporaryDirectory()`), plus an asyncio.Semaphore sized to available CPUs. This is exactly what the maintained unoserver project does — its server.py line 91 passes `-env:UserInstallation={self.user_installation}` built from a temp dir (line 670).
- source: Local Docker concurrency experiments (--cpus=4 and --cpus=1); unoserver 3.7 source, unoserver/server.py lines 91 and 670
- IMPACT: Never share a profile. Per-invocation temp profile is mandatory, not optional. Size the LibreOffice semaphore to vCPUs, NOT to the 4-6 concurrency target used for the Claude fan-out — those are unrelated limits and conflating them will hurt. On a Fly shared-cpu-1x (1 vCPU) set LO concurrency to 1: parallel conversion buys zero throughput and multiplies memory. ### fly-deploy
**[PARTLY_TRUE]** With auto-stop disabled, in-flight jobs are safe.

- evidence: Autostop is only one of several things that stop a machine. Fly's blueprint lists the others under "The machine stops mid-job even with auto_stop_machines = 'off'": "Deploys, `fly machine stop`, scale-down, and host migrations all do too." On any stop, "Fly sends kill_signal (default: SIGTERM) to PID 1. After waiting kill_timeout seconds, it sends SIGKILL." Defaults: `kill_signal = SIGTERM`, `kill_timeout = 5s`, max `300s`. The config reference adds a warning: "kill_timeout settings should be considered best-effort, and your app needs to be prepared to handle shorter stopping times." The blueprint is blunt about what kill_timeout is for: "kill_timeout is not a 'finish your work' timer. It's a drain window... If your jobs take longer than 5 minutes, you can't drain them inside kill_timeout. You need either Pattern A with checkpoint/resume, or Pattern B with a worker tier." Also: `fly secrets set` "updates each Machine belonging to that Fly App. This involves a restart of the Machine" — so rotating the Anthropic key mid-job kills the job unless you use `--stage`. Separately, PID 1 must actually be your app: "In a container running a shell wrapper (CMD ["sh", "-c", "..."]), the shell is PID 1 and SIGTERM doesn't propagate. Use the exec form."
- source: https://fly.io/docs/blueprints/long-running-tasks/ , https://fly.io/docs/reference/configuration/#runtime-options , https://fly.io/docs/apps/secrets/
- IMPACT: Jobs must be crash-safe, not just autostop-safe. Concretely: (1) persist per-topic pass-2 state in SQLite so a killed job resumes rather than restarts (this also protects your prompt-cache economics — a resumed job re-pays the cache write); (2) on boot, scan for jobs in a `running` state with no live worker and either resume or mark `interrupted`; (3) set `kill_signal = "SIGTERM"`, `kill_timeout = "300s"` (the max) and install an asyncio SIGTERM handler that stops accepting work and drains, with an internal deadline ~10s under the timeout; (4) use `CMD ["python", ...]` exec form or an `exec` in the entrypoint; (5) always use `fly secrets set --stage` then deploy at a quiet moment. Also run `fly config validate --strict` — Fly warns that plain `fly config validate` "silently accepts unrecognized sections and keys", so a typo'd `auto_stop_machines` would pass and do nothing.
**[PARTLY_TRUE]** Server-Sent Events work through Fly's proxy without buffering or premature timeouts, with no special config.

- evidence: SSE works, but three proxy behaviors need attention. (1) COMPRESSION BUFFERING — documented: "The proxy buffers responses before compressing them. That can break HTML streaming—e.g., progressive server-side rendering. To avoid buffering, disable compression by setting Content-Encoding: none for those responses." The proxy auto-negotiates zstd/br/gzip on any response that does not already carry a Content-Encoding header. There is also an undocumented-in-the-reference `compress` boolean in `[http_service.http_options]` (present in the fly-go `HTTPOptions` struct alongside `idle_timeout`, `h2_backend`, `headers_read_timeout`). Community reports of SSE arriving in ~5s batches match this compression-buffer behavior. (2) IDLE TIMEOUT — historically 60s of no bytes in either direction closed the connection (Fly staff, jerome: "60 seconds without any data being sent or received will cause the connection to be closed"; "As long as they send something within 60 seconds of the last sent packet"). Fly removed the blanket TCP idle-timeout in Sept 2023 ("long-lived connections won't be closed anymore when there's no read/write activity"), and `idle_timeout` is now an explicit fly.toml knob: `[http_service.http_options] idle_timeout = 600`. The default value is not stated in the docs. (3) HTTP/2 + WebKit — a July 2026 report shows 1-3KB SSE events arriving seconds late on iOS/WebKit over Fly's h2 edge, instant over curl h2, instant over the same phone with `[http_service.tls_options] alpn = ["http/1.1"]`, and instant on AWS ALB h2 with the identical image.
- source: https://fly.io/docs/reference/content-encoding/ , https://fly.io/docs/reference/configuration/#http_service-http_options-idle_timeout , https://community.fly.io/t/request-timeouts-on-fly-io/5653 , https://community.fly.io/t/tcp-idle-timeouts-restrictions-have-been-removed/15160 , https://community.fly.io/t/sse-events-delayed-several-seconds-for-ios-webkit-clients-over-http-2/28307
- IMPACT: Set `Content-Encoding: none` (plus the usual `Cache-Control: no-cache`, `X-Accel-Buffering: no`) on the SSE response — this is the documented fix and it is not optional. Set `[http_service.http_options] idle_timeout = 600` and emit an SSE heartbeat comment (`: ping\n\n`) every 15-20s regardless; a pass-2 topic call can easily go 60s+ with nothing to report. If iOS users see laggy progress, the escape hatch is `[http_service.tls_options] alpn = ["http/1.1"]`. Architecturally: because the user may close the tab and because Fly restarts kill streams, SSE must be a read-only VIEW over job state in SQLite (client sends `Last-Event-ID`, server replays from the DB), never the transport of record.
**[REFUTED]** Secrets are set via `fly secrets set`, injected as environment variables, and are available at build time.

- evidence: Runtime only. "An app's secrets are available as environment variables at runtime on every Machine belonging to that Fly App." And explicitly: "You can set secrets for your applications, but these are only available at run-time. They aren't available when building your Docker image without a little extra work." Build-time access requires Docker BuildKit secret mounts — `RUN --mount=type=secret,id=MY_SECRET ...` reading from `/run/secrets/<id>` — plus `fly deploy --build-secret MY_SECRET=value` on every deploy. Mechanics: values are stored in an encrypted vault, the API can encrypt but not decrypt, values are never logged and cannot be read back (`fly secrets list` shows name + digest only). `fly secrets set` restarts every Machine (and resets the ephemeral filesystem); `--stage` defers that to the next deploy. Secrets can also be materialized as files via `[[files]] guest_path=... secret_name=...`, but the secret value must be base64-encoded.
- source: https://fly.io/docs/apps/secrets/ , https://fly.io/docs/apps/build-secrets/
- IMPACT: `ANTHROPIC_API_KEY` and the shared `APP_PASSWORD` are runtime secrets — fine, that's all this app needs. Do NOT bake anything into the image. Be aware `fly secrets set` without `--stage` is a machine restart, which under this design kills any running generation job; always `fly secrets set --stage` then deploy deliberately.
**[REFUTED]** There is a hard HTTP request-duration or body-size limit through Fly's proxy that would break a 150MB upload.

- evidence: No documented cap on request duration or request body size for ordinary proxied requests. The only size threshold in the docs is the replay/retry buffer: "To prepare for the possibility of receiving fly-replay... or for retrying failed requests, Fly edge proxies buffer requests up to 10MB. If a request grows larger than 10MB, buffering stops, making it impossible to replay or retry the request. When this happens, PA01 is emitted." PA01 is informational — it means the request cannot be replayed, not that it is rejected. Separately, the fly-replay feature itself is documented as "Requests larger than 1MB cannot be replayed", with Fly's own suggested remedy "For large uploads that exceed the 1MB limit, consider: Using direct-to-storage uploads where possible" and using the `fly-prefer-region` header, "Useful for large uploads that can't be replayed." Neither applies to a single-machine, single-region app — there is nothing to replay to. The remaining constraint is the idle timeout, which resets on every byte: Fly staff, "That 60s timeout resets when you send any data at all" / "As long as they send something within 60 seconds of the last sent packet." A steadily-uploading 150MB body never idles.
- source: https://fly.io/docs/monitoring/error-codes/#pa01-replay-retry-buffer-exceeded , https://fly.io/docs/networking/dynamic-request-routing/ , https://community.fly.io/t/request-timeouts-on-fly-io/5653
- IMPACT: A 150MB multipart POST will go through. But make it robust rather than lucky: (a) upload files ONE AT A TIME from the browser rather than one 150MB multipart request — smaller blast radius on failure, real per-file progress, and it keeps you under the 10MB replay buffer per request only incidentally (that's not the reason); (b) on the server, stream the body to the volume — Starlette's UploadFile spools to memory up to ~1MB then to a tempfile, so set `TMPDIR` to a path on the mounted volume, otherwise you spool onto the slow 2000-IOPS / 8 MiB/s ephemeral rootfs; (c) enforce the 50MB/file and 150MB/job caps server-side as you stream, not after buffering; (d) raise `idle_timeout` to 600 so a slow uplink with TCP backpressure stalls don't trip it. If you ever want this bulletproof, Fly's own advice is direct-to-object-storage (their Tigris extension) with the app only receiving keys.

## Gotchas

### genanki
- deck_id=1 is silently destructive. `Deck.write_to_db` does `decks.update({str(self.deck_id): self.to_json()})` against a col whose decks JSON already contains key "1" (Anki's Default deck), so id 1 OVERWRITES Default. Verified: a card in `Deck(1,'Bio::Ch1')` landed in 'Default' after import, while the identical deck with id 1987654321 landed correctly in 'Bio::Ch1'. Generate deck ids as large ints (e.g. uuid5 of the deck path mod 1<<31) and assert id != 1.
- Duplicate deck_ids collapse decks silently. Two Deck objects sharing a deck_id in one Package: the dict update means the LAST name wins and ALL notes from both land in that one deck. Verified: Deck(777000111,'X::A') and Deck(777000111,'X::B') produced both notes in 'X::B' with no error. Derive deck ids deterministically from the full '::' path and assert uniqueness before building the Package.
- Tags cannot contain spaces — genanki RAISES. `_TagList._validate_tag` throws `ValueError: Tag "..." contains a space; this is not allowed!` on append/extend/insert/setitem. Your planned tags for topic/difficulty/source page are exactly the danger zone: 'topic::cell biology' and 'source page 12' both raise. Verified. Sanitize with `re.sub(r'\s+','_',tag)` at the boundary. Note this is a hard exception, not a warning, so an unsanitized LLM-derived topic name will crash the whole deck build.
- LLM output must be HTML-escaped or it will be silently corrupted. Anki fields store raw HTML. genanki's `_check_invalid_html_tags_in_fields` only warns on MALFORMED tag-like text, and its regex treats plausible-looking sequences as valid: I verified that 'code: a<b && c>d' produces NO warning, yet Anki will render '<b && c>' as a bold tag and swallow the text. Call `html.escape()` on every LLM-produced field — but NOT on cloze markup, and not on the `<img>` tags you inject yourself. Escaping after cloze-marker insertion will break the cloze; sequence it carefully.
- Media files are keyed by BASENAME, so same-named images from different sources silently clobber each other. `media_json = {idx: os.path.basename(path)}`. Verified: passing 'ma/fig1.png' and 'mb/fig1.png' produced manifest {"0":"fig1.png","1":"fig1.png"} and only ONE file survived in Anki's media dir. This will bite hard once Image Occlusion lands and you extract 'image1.png' from several PDFs. Rename every extracted asset to a content-hash filename before adding it to media_files, and reference that hash in the <img src>.
- Reorganising the topic tree strands existing cards. Because Anki updates notes WITHOUT touching cards, a card whose deck path changes between regenerations does NOT move. Verified: a note in 'Bio::Chapter 3::Glycolysis' regenerated under 'Bio::Chapter 9::Cellular Respiration' had its fields updated but its card stayed in the Chapter 3 deck — while the new empty Chapter 9 decks were created anyway. Since your UI lets users edit the topic tree and then regenerate, this produces stale decks plus a litter of empty new ones. Either treat deck path as immutable once a card UUID is issued, or surface 'this card will stay in its original deck' in the UI, or mint new UUIDs on reparent (which forfeits scheduling).
- genanki's built-in Models are module-level MUTABLE singletons and `Model.to_json` mutates them in place — it assigns `tmpl['ord']`, `field['ord']` and setdefaults into `self.templates`/`self.fields`, and `Model._req` is a `cached_property`. With an in-process background worker running concurrent jobs that all share `genanki.BASIC_MODEL`, two simultaneous Package builds touch the same objects. The mutations are idempotent so this is very likely benign, but it is not designed for concurrency. Serialize the final .apkg assembly step behind a lock — it is fast and single-threaded anyway — rather than letting parallel jobs build packages simultaneously.
- `Model.to_json(timestamp, deck_id)` stamps the model's "did" with whichever deck wrote it last, so in a multi-deck package the shared BASIC_MODEL ends up pointing at an arbitrary deck. Harmless for card placement (cards carry their own did, verified) but it means the notetype's default deck in the user's collection is effectively random. Ignore it, but do not be alarmed when you see it in the DB.
- Anki's apkg importer matches ONLY on GUID — never on first-field content. There is no first-field dedup on this path. Two cards with identical fronts but different UUIDs will both import as separate notes and Anki's browser will later flag them as duplicates. If pass 2 runs per-topic in parallel with the full document in context, the same fact will very plausibly be generated under two topics. Dedup semantically on your side before assigning UUIDs; Anki will not do it for you.
- Deck name components need sanitizing beyond just avoiding '::'. Anki's name normalization has sharp edges I confirmed in its test suite: 'foo::::baz' becomes 'foo\x1fblank\x1fbaz' (an empty component is silently renamed to the literal 'blank'), 'foo:::bar' collapses to two components, trailing whitespace is stripped, and newlines and \x1f are removed. An LLM-generated topic title like 'Chapter 3: Glycolysis' is fine (single colon survives), but any title containing '::' will accidentally create an extra nesting level. Strip '::' from each individual topic name before joining the path, and reject empty components.
- Anki caps deck nesting at 11 levels (`require!(recursion_level < 11, "deck nesting level too deep")` in first_existing_parent). Your topic tree is user-editable, so clamp depth server-side — a runaway pass-1 plan producing a deep tree would fail the import rather than degrade.
- Note IDs are generated from `itertools.count(int(timestamp*1000))` and cards from the same counter, so a single Package is internally consistent — but Anki's importer reassigns ids on collision anyway (`uniquify_note_id` bumps by 999). Do not attempt to use genanki's note ids as your stable identity; the GUID is the only stable handle, which is exactly what your design already assumes. Just never let two cards share a UUID, or the second silently overwrites the first on import.

### anki-import
- A card flipping between Basic and Cloze on regeneration is the single worst failure mode, and your design invites it ("mixed Basic + Cloze note types chosen per card"). With merge_notetypes OFF the note is silently dropped (conflicting=1, old content retained, junk notetype left behind). With merge_notetypes ON, Anki raises a hard BackendError — "Cloze note types cannot be merged with regular note types." — which ABORTS THE ENTIRE IMPORT inside the transaction, so nothing at all is imported. Fix: persist the chosen note type alongside the card UUID in SQLite and treat it as immutable. If pass 2 wants to change a card from Basic to Cloze, you must mint a NEW UUID and let the old note die (or be deleted by the user), never reuse the GUID.
- Deck placement is write-once. A card lands in whatever deck the .apkg names on its FIRST import and never moves again, no matter how many times you regenerate. Your pass-1 topic-tree reorganisation will therefore never take effect for existing cards — it will only litter the user's deck list with empty duplicate subdecks. Worse, when an existing note gains a card (a new cloze ordinal), the new card goes into the NEW deck while its sibling stays in the OLD one, splitting one note's cards across two decks. Decide now: freeze the deck path per UUID at first export, and carry mutable topic identity in tags instead.
- Tags are replaced wholesale on update, not merged. Every regeneration wipes any tag the user added by hand, plus Anki's own `marked` and `leech` tags. Coloured flags survive (they live on the card), tags do not. Either mirror this in the UI as expected behaviour or don't regenerate over notes the user has tagged.
- Removing a cloze deletion does not remove its card. Regenerating a note from {{c1::x}} and {{c2::y}} down to just {{c1::x}} updates the text but leaves the ord=1 card in place, complete with its review history, now rendering blank. Verified: col.get_empty_cards() reports it, but only Tools > Empty Cards actually deletes it, and the user must do that manually. Same applies to any card count reduction. Only ever grow a note's cloze ordinals; never renumber or reuse them.
- Update is gated on note mtime, and genanki writes note.mod = int(timestamp) with 1-second resolution. Two consequences: (a) never pass a fixed/hermetic timestamp to Package.write_to_file for real exports or updates will be skipped forever; (b) if a user edits a note in Anki, their edit makes the note newer than your next export only until your next export — the default IF_NEWER means whoever touched it last wins, so a regeneration silently clobbers user edits (and, in the reverse timing, a user edit silently blocks your regeneration). Neither is obviously right; pick one and say so in the UI.
- genanki's Model.model_id and the exact field/template list form a schema you can never change. Any change to fields or templates on an existing model_id makes Anki create a duplicate notetype ('YourModel+') and DROP every affected note from the import, with the only recovery being the user manually enabling the collapsed 'Merge note types' option. Hard-code the model_ids as constants in source, add a test that asserts the field/template lists never change, and version new shapes as new model_ids.
- Even when 'Merge note types' does rescue a schema change, the field-addition rewrites every existing note and bumps its mtime to now — so under the default IF_NEWER the note's CONTENT update is skipped in that same import. Users would need to import the file a second time. Another reason to freeze models rather than rely on merge.
- You are only verified against Anki DESKTOP 26.08 (rslib). AnkiDroid and AnkiMobile ship their own builds of the same Rust backend, so behaviour should match, but version skew is real and the update-in-place semantics only date from 23.10. Worth stating a minimum supported Anki version (23.10+, realistically 24.x+) on the download page rather than assuming.
- genanki 0.13.1 writes the legacy schema-11 `collection.anki2` format. This imports fine, but it means the .apkg is uncompressed SQLite plus raw media and will be noticeably larger than a modern anki21b export. With a 200-page/150MB job cap and image cards later, keep an eye on download size; there is no option in genanki to emit the modern format.
- genanki writes csum=0 for every note and relies on Anki to recompute it. That is fine for import, but it means the .apkg itself carries no first-field duplicate detection — GUID is your only identity mechanism. Make the per-card UUID generation deterministic and stored in SQLite before the first export, never derived from card content (genanki's default guid_for(*fields) hashes the fields, so any content edit would change the GUID and orphan the review history — you must always pass guid= explicitly).

### image-occlusion
- The imported Image Occlusion notetype ALWAYS lands as a second, duplicate notetype in the user's collection — I confirmed it gets auto-renamed "Image Occlusion+". Cause: stock notetype ids, field ids and template ids are randomly generated per collection (I verified two fresh collections produce entirely different ids), so the importer can never match ours to theirs. `ImportAnkiPackageOptions(merge_notetypes=True)` does NOT help — I tested it. This happens with the official `anki` exporter too, not just genanki, so it is not a genanki defect. Mitigation: name yours something unambiguous like "Image Occlusion (ai-anki)" so the user sees an intentional name instead of a mysterious "+" clone. Anki still treats it as a real IO note because matching is on originalStockKind, not name.
- Re-import does NOT update notes in place unless the note's `mod` timestamp is strictly NEWER. The default is `ImportAnkiPackageUpdateCondition.IF_NEWER` (enum value 0). My first test regenerated a deck within the same second and the edits were silently discarded — field stayed at 'v1'. When I bumped the package timestamp, the update landed: same note id, fields updated, and ivl=42/reps=7 scheduling preserved. genanki sets note mod from the package timestamp, so pass an explicitly increasing `timestamp=` to `Package.write_to_file`, or a same-minute regenerate-and-reimport will look like a silent no-op to your users. This validates the stable-GUID design, but only with that caveat.
- Field names in the stock IO notetype are LOCALIZED (built from tr.notetypes_occlusion(), tr.notetypes_image(), ...). In English they are 'Occlusion' (singular — not 'Occlusions', despite the Rust field-index struct being named occlusions), 'Image', 'Header', 'Back Extra', 'Comments'. Anki resolves them by the numeric `tag` (0..4) with a positional 0/1/2/3 fallback, so ALWAYS emit the `tag` values. Never look a field up by the string 'Occlusion'.
- The IO notetype must be type=1 (Cloze) AND have at least 4 fields, or Anki rejects it: io_notetype_if_valid() raises "IO notetype must have 4+ fields", and get_io_field_indexes() returns DatabaseCheckRequired if the tags are missing and there are <4 fields.
- Shapes smaller than 5px are dropped by Anki's own editor, and `width`/`height`/`rx`/`ry` values of exactly "0" are stripped during rendering (is_empty_or_zero in imageocclusion.rs). A vision model that returns a degenerate box will produce an invisible mask and a card that shows nothing — validate a minimum normalized size (e.g. >= 0.01 of each axis) before emitting.
- Anki's mask geometry is normalized against the IMAGE's dimensions, so the exact PNG you send to Claude must be the exact PNG you put in the .apkg media. If you send Claude a pre-resized version but ship the original to Anki, the masks still land correctly (fractions are scale-invariant) — but if you crop for accuracy and ship the uncropped image, every mask is wrong. Ship whatever you cropped.
- Anki caps rendering at 8000x8000 and the API caps images at 10 MB base64 / 8000x8000 px; more importantly, requests with >20 image-or-document blocks impose a stricter per-image dimension limit (resize to <=2000 px per side or keep to <=20 blocks). A 200-page job that rasterizes many diagram pages will hit this before it hits your 150 MB job cap.
- AnkiMobile can STUDY built-in IO cards but (as of the 23.10 line) could not create them; AnkiDroid needed 2.17+, and there are open bug reports about IO rendering on mobile (ankidroid/Anki-Android#16323). Since ai-anki generates the notes server-side, creation-side gaps do not matter — but tell users their phone client must be current or the cards render blank.
- `anki` on PyPI is AGPL-3.0-or-later and ships as binary-only abi3 wheels tagged manylinux_2_35. If you ever add it even as a test dependency, make sure the Dockerfile base is glibc >= 2.35 (python:3.12-slim/bookworm = 2.36 is fine; Alpine/musl and bullseye are not), and keep it out of the runtime image so the network-copyleft clause is never triggered by the deployed service.
- genanki is effectively in maintenance mode: last PyPI release 0.13.1 on 2023-11-12, last repo commit 2024-12-30, 36 open issues. It works fine and its output format (schema 11) is still accepted by Anki 26.8 — I verified that today — but assume no upstream help. Vendor or pin it, and add an `anki`-lib-based CI test that actually imports your generated .apkg and asserts card counts and rendered HTML; that test is the real safety net, and it caught both the duplicate-notetype and the mod-timestamp behaviours above.

### anthropic-docs
- THE 200-PAGE CAP CAN BLOW THE 1M CONTEXT WINDOW — this is the real binding constraint, not the 600-page limit. At the documented ~1,500–3,000 text tokens/page PLUS a page image (up to 4,784 visual tokens on Opus 5's high-res tier), 200 pages is roughly 600K–1.5M input tokens. The upper half of that range does not fit in 1M. The docs warn about exactly this: "Dense PDFs (many small-font pages, complex tables, or heavy graphics) can fill the context window before reaching the page limit. Requests with large PDFs can also fail before reaching the page limit, even when using the Files API." Fix: gate job admission on `client.messages.count_tokens()` against the assembled document blocks, not on page count or MB. A ~700K-token ceiling leaves room for output. Consider lowering the page cap to ~100–120 for image-heavy/scanned material.
- PASS 1 AND PASS 2 MUST SHARE A BYTE-IDENTICAL CACHED PREFIX OR THE 1-HOUR CACHE IS WORTHLESS. Cache render order is tools -> system -> messages, and a cache write happens ONLY at your `cache_control` breakpoint (the lookback finds prior *writes*, not stable content). If pass 1 uses a "deck planner" system prompt and pass 2 uses a "card writer" system prompt, the prefix diverges *before* the documents and pass 2 gets zero cache hits on ~1M tokens — a ~$5 miss per call, times every topic. Fix: use ONE identical system prompt (and identical `effort` and identical `thinking` config — all three are rendered into the prompt) for both passes, put the document blocks next with `cache_control: {type:"ephemeral", ttl:"1h"}` on the LAST document block, and put all pass-specific instructions in a text block AFTER the breakpoint.
- FIRING 4-6 PASS-2 CALLS IN PARALLEL DEFEATS THE CACHE ENTIRELY. Verbatim from prompt-caching.md: "For concurrent requests, note that a cache entry only becomes available after the first response begins. If you need cache hits for parallel requests, wait for the first response before sending subsequent requests." If all 6 fire simultaneously against a cold cache, all 6 pay the full 1-hour cache-WRITE price (2x base = $10/MTok on Opus 5) on the whole document. On a 1M-token doc that is ~$60 instead of ~$12.50. Fix: fire exactly one topic call first, await the first streamed token (not the full response), then fan out the rest. The asyncio worker needs an explicit priming step, not a bare `asyncio.gather`.
- THE USER APPROVAL STEP CAN OUTLIVE THE 1-HOUR CACHE TTL. The design has a human editing/approving the deck plan between pass 1 and pass 2. If that takes over an hour — closing the laptop, coming back after dinner — the cached prefix expires and pass 2 pays a full cold write again. Consider re-warming the cache when the user hits Approve (a `max_tokens: 0` prefill request writes the cache and returns immediately with `content: []`), or surface a "plan expires in 55 min" hint. Note `max_tokens: 0` is rejected with `stream: true`, `output_config.format`, or forced `tool_choice` — send the warm-up as a plain non-streaming request.
- COST REALITY CHECK AT THE 200-PAGE CAP. Opus 5 pricing: $5/MTok base input, $10/MTok for 1-hour cache writes, $0.50/MTok cache reads, $25/MTok output. A ~1M-token job = ~$10 for the one cache write + ~$0.50 per pass-2 topic call. With 15 topics that is ~$17.50 of input alone, before thinking and card output at $25/MTok. A handful of friends generating a few decks each will run real money. Worth a per-job cost estimate shown before the user confirms, and a hard per-job token budget.
- SDK FORCES STREAMING ABOVE max_tokens = 21,333. From thinking.md: "The SDKs require streaming when `max_tokens` is greater than 21,333, to avoid HTTP timeouts on long-running requests. This is a client-side validation, not an API restriction." Since thinking is ON by default on Opus 5 and counts against `max_tokens`, a pass-2 call generating 30 cards will want a roomy `max_tokens` and will therefore trip this. Use `client.messages.stream(...)` + `.get_final_message()` in the background worker. Same doc also advises: "For workloads that push thinking above roughly 32k tokens per request, use batch processing to avoid networking issues."
- MORE THAN 20 IMAGE BLOCKS IN ONE REQUEST TRIGGERS A STRICTER 2000px PER-IMAGE LIMIT. vision.md: "If a single API request contains more than 20 images, a stricter per-image dimension limit applies... Images exceeding the stricter limit are rejected with an `invalid_request_error` whose message references 'many-image requests'... either resize each image so that neither dimension exceeds 2000 px, or keep the request to 20 or fewer image and document blocks." A student uploading 40 phone photos of lecture slides hits this. Fix: downscale any uploaded PNG/JPEG to <=2000 px on ingest. (Note: on the first-party Claude API, PDF `document` blocks do NOT count toward the 20 — that threshold includes document blocks only on Bedrock and Google Cloud.)
- SCANNED PDFs SILENTLY LOSE PAGE PROVENANCE. Relying on Claude vision instead of an OCR layer is supported for *reading*, but citations.md is explicit: "As image citations are not yet supported, PDFs that are scans of documents and do not contain extractable text are not citable." Combined with the citations/structured-outputs 400, this means the `source page` tag will always be model-self-reported, never API-verified. Do not surface it to users as authoritative.
- PYDANTIC SELF-REFERENCING MODELS WILL 400. If the deck-plan model is written the natural way (`class Topic(BaseModel): subtopics: list["Topic"]`), it emits a recursive `$ref` and structured outputs rejects it — recursive schemas are unsupported. Flatten to `path: str` using the same `::` separator Anki uses, which conveniently makes the plan JSON map 1:1 onto the subdeck names. Related trap: the Python SDK *silently strips* unsupported constraints (`ge`, `le`, `max_length`, `maxItems`) and folds them into field descriptions, so `Field(ge=1, le=30)` on card counts becomes a suggestion, not a guarantee — clamp in Python after parsing.
- STRUCTURED OUTPUTS REORDER YOUR JSON KEYS. "Required properties appear first, followed by optional properties." If the UI or any diffing logic depends on key order in the deck plan, either mark every property required or normalize after parsing. Also, `enum` capitalization is not guaranteed — compare `note_type` ("Basic"/"Cloze") and difficulty values case-insensitively, or the mapping to genanki note types will intermittently fail.
- FIRST REQUEST WITH A NEW SCHEMA PAYS A COMPILATION LATENCY PENALTY; compiled grammars are cached 24h and invalidated by schema *structure* changes (not name/description changes). Irrelevant at this scale, but it means the first job after any deploy that touches the deck-plan schema will feel slower — don't chase it as a bug.
- `thinking: {type: "disabled"}` IS A TRAP ON OPUS 5 IF YOU EVER REACH FOR IT TO CUT COST. It returns a 400 when combined with `effort: xhigh` or `max` (validated per request, so it can pass early and fail later if effort is ever raised), and the docs warn that with thinking disabled "Claude Opus 5 can occasionally emit tool calls as plain text or include internal XML tags in its visible output." Lower `effort` to `medium`/`low` instead — those are the documented cost levers.
- TXT AND MD DON'T NEED THE CONVERSION PIPELINE. files.md: plain-text files uploaded with MIME type `text/plain` are first-class `document` blocks by `file_id`. Routing .txt/.md through a `document` block rather than inlining them as a text block keeps them inside the same cached prefix as the PDFs and avoids bloating the request body — one fewer special case in ingestion.

### prompt-caching
- EFFORT AND THINKING CONFIG INVALIDATE THE CACHE — this is the biggest thing not in your design doc. Docs: "The thinking configuration and the resolved effort level are rendered into the prompt itself, so changing any of them starts a new cache prefix... message-level breakpoints always miss, and tool and system-prompt breakpoints can miss too." On claude-opus-5 thinking is ON BY DEFAULT (omitting the field runs adaptive). If pass 1 runs at effort high and pass 2 at effort medium (a natural cost optimization), your document cache is destroyed and every topic call pays full price. Pin one explicit effort and one explicit thinking config in a shared constant used by both passes. Note also: setting a parameter explicitly to its model default is equivalent to omitting it and does NOT invalidate.
- CACHE READS ARE NOT DEDUCTED AGAINST YOUR RATE LIMIT — docs list this as a reason to use the 1h cache. This is arguably a bigger deal than cost for you: 6 concurrent uncached calls each carrying a ~400K-token document is ~2.4M input tokens in a burst, which will hit ITPM limits and 429 on most tiers. Getting the sequencing right converts almost all of that into rate-limit-free cache reads. Budget your concurrency against ITPM assuming reads are free and only the post-breakpoint suffix counts.
- STRUCTURED OUTPUTS vs THE CACHE IS UNVERIFIED. output_config.format is NOT listed in the invalidation table, but pass 1 (JSON deck plan) will likely use it while pass 2 may not, or may use a different schema. Whether the schema is rendered into the prompt ahead of messages is undocumented. Measure this empirically before committing: run pass 1 with output_config.format and pass 2 without, and check pass 2's cache_read_input_tokens. If it is zero, either use structured outputs on both passes with the same schema, or use neither. Related: max_tokens: 0 pre-warming is REJECTED when output_config.format is set, so if you rely on structured outputs you cannot pre-warm with the identical request shape.
- 32MB REQUEST LIMIT vs YOUR 50MB-PER-FILE AND 150MB-PER-JOB CAPS. Base64-inline PDF document blocks are subject to a 32MB request-size limit. A 50MB PDF cannot be sent inline at all, and base64 inflates by ~33%, so the practical inline ceiling is ~24MB of raw PDF. Use the Files API (beta header files-api-2025-04-14) and reference documents by file_id instead — file-source document blocks are still ordinary document content blocks and remain cacheable. This also avoids re-uploading a 400K-token document body on every one of your 4-6 parallel pass-2 calls, which is a real wall-clock and bandwidth cost even when the tokens are cached.
- THE 1-HOUR TTL IS A CLOCK ON YOUR UI, NOT JUST A COST KNOB. The window between pass 1 finishing and the user approving the deck plan is human-paced. If the user walks away for 90 minutes, the entry expires and every pass-2 call pays a full uncached read plus a write. Mitigations: (a) show the plan-approval step with a visible freshness indicator; (b) re-warm with a max_tokens: 0 request just before fanning out if more than ~50 minutes have elapsed; (c) note that cache hits refresh the TTL for free, so a cheap periodic touch keeps it alive. Also relevant to your 30-day re-generation feature: a regenerate run days later always pays the full cold write.
- MIXED TTLs HAVE AN ORDERING CONSTRAINT: "Cache entries with longer TTL must appear before shorter TTLs (that is, a 1-hour cache entry must appear before any 5-minute cache entries)." If you ever add a second breakpoint (e.g. 1h on the document, 5m on a per-job preamble), the 1h one must come first in render order or billing behaves unexpectedly.
- 20-BLOCK LOOKBACK + NON-DETERMINISTIC FILE ORDER. The lookback checks at most 20 positions per breakpoint. If a job has many uploaded files rendered as separate document blocks, and your ingestion emits them in filesystem or dict order rather than a deterministic sort, the prefix bytes differ between pass 1 and pass 2 and nothing matches. Sort the file list deterministically (by stable ID, not by name or mtime) and freeze the block order in SQLite at job creation so pass 2 reconstructs byte-identical content.
- CACHES ARE ISOLATED PER WORKSPACE on the Claude API (not just per organization). If you ever split dev/prod into separate workspaces under one org, they will not share caches. Harmless now, but it means load-testing in a dev workspace tells you nothing about prod cache state.
- max_tokens: 0 PRE-WARM RESTRICTIONS, if you adopt that pattern: rejected with stream: true, with extended thinking (thinking.type: "enabled" — adaptive is fine, which is what Opus 5 uses), with output_config.format, with tool_choice of {type: tool} or {type: any}, and inside a Batches request. It still incurs a normal cache-write charge. Put the breakpoint on the last block SHARED with the real request, never on the placeholder user message, and use the same thinking/effort config or you write an entry your real traffic never hits.
- DO NOT BATCH PASS 2 AS A COST OPTIMIZATION without understanding the cache interaction. The Batches API gives 50% off but docs warn: "because asynchronous batch requests can be processed concurrently and in any order, cache hits are provided on a best-effort basis." Combined with your SSE progress UI and interactive UX, batching is the wrong tool here — your synchronous fan-out with a warm 1h cache is both faster and more predictable.

### libreoffice
- THE BIG ONE — soffice's exit code is unreliable in BOTH directions, so you must verify the output file instead. Verified on both amd64 and arm64: a truncated DOCX returns **exit code 0**, prints "Error: source file could not be loaded" on STDOUT, and produces NO PDF. Meanwhile a profile clash under concurrency returns **exit code 1** with NO error message at all. Never branch on returncode. The only reliable success test is: the expected `<basename>.pdf` exists in outdir AND its size is > 0. A naive `check=True` subprocess call will happily report success on a file that never converted.
- Output filename collision causes silent overwrite. The output name is always `<input-basename>.pdf`, derived from the input, with no uniquification. Two users both uploading `lecture.pptx` into the same outdir will silently clobber each other — I verified the second conversion overwrote the first (76772 -> 287900 bytes, same path, no warning). Give every job its own output directory keyed by job/file UUID; do not rely on the original filename anywhere.
- Garbage inputs produce valid-but-empty PDFs that will burn Claude tokens. A 0-byte `.docx` and a plain-text file renamed `.docx` both converted "successfully" (exit 0, real PDF produced) into blank or near-blank PDFs. Since the design sends these straight to Claude as PDF document blocks against a 200-page cap, you will pay full price to have Opus read empty pages. After conversion, sanity-check the PDF (page count, and that some text or image content exists) before it enters the Claude pipeline — and surface a clear "we couldn't read this file" error to the user instead.
- Page count is not slide/page count — budget the 200-page cap accordingly. My 40-section DOCX rendered to **80** PDF pages. DOCX has no intrinsic page count until it is laid out, so you cannot enforce the 200-page cap before conversion. Enforce it *after* the PDF exists (count pages with pypdf), or users will slip well past the cap and blow up context size and cost. Note also that font substitution can shift pagination, so the count is not stable across image rebuilds.
- On Fly.io, memory is the binding constraint, not CPU. Peak RSS measured ~218 MB for a single conversion. A 256 MB Fly machine will OOM on one conversion; 512 MB is uncomfortably tight given FastAPI plus the SQLite worker are in the same container. Budget >=1 GB. And because shared-cpu-1x gives zero throughput gain from parallel conversion (measured perfectly linear: 2.9s / 5.9s / 12.3s for N=1/2/4), set the LibreOffice semaphore to 1 there — parallelism only multiplies the memory risk.
- Keep the LibreOffice semaphore separate from the Claude fan-out semaphore. The design targets 4-6 concurrent Claude calls; that number is about API concurrency and has nothing to do with CPU-bound LibreOffice. Sharing one limit means either starving the Claude fan-out or OOM-ing on conversions. Two independent semaphores.
- Set XDG_CACHE_HOME (or HOME) to a writable dir even though you pass -env:UserInstallation. With a read-only rootfs I saw repeated `Fontconfig error: No writable cache directories`. Conversion still succeeded, but fontconfig re-scans fonts on every single invocation instead of using a cache, which is wasted startup time on every job. Point HOME at the same per-job temp dir you use for the profile — cheap and removes the log noise.
- Debian bookworm ships LibreOffice 7.4.7.2, which is several years old. It converted everything I threw at it correctly, so this is not a blocker, but if you hit a specific rendering bug in a modern PPTX the fix is to move the base image to trixie rather than to debug 7.4. Worth knowing before you spend hours on a layout quirk.
- Do NOT install a JRE to silence the javaldx warning. Every single run prints `Warning: failed to launch javaldx - java may not function correctly`. It is harmless for Writer/Impress PDF export — all my conversions succeeded with no JRE present. Installing default-jre would add 100+ MB to the image to suppress a cosmetic log line. Filter it out of your logs instead, and note that this warning is *not* a useful failure signal.
- Clean up the per-job profile directory explicitly, and mind the disk. Each fresh profile is a real directory tree (config, basic, extensions, gallery, database subdirs). `tempfile.TemporaryDirectory()` as a context manager handles this, but if a conversion is killed by your timeout the directory can leak. Since the design mounts a persistent Fly volume, put profiles on /tmp (tmpfs), never on the volume, or slow leaks will eat the disk that SQLite and uploads depend on.
- Always wrap the subprocess in an explicit timeout and kill the process on expiry. I could not induce a hang in any test, but LibreOffice is well known to block on password-protected documents (it wants to prompt for a passphrase, and headless mode has nowhere to prompt). Since users will upload arbitrary study material, an encrypted DOCX/PPTX is a realistic input. Use asyncio.wait_for + proc.kill(), and detect encrypted files up front with msoffcrypto-tool so you can return a clean error rather than eating a 180 s timeout slot in the worker.

### fly-deploy
- `release_command` machines do NOT mount your volume. The docs are explicit: "Volumes are also not mounted to the temporary Machine created when using a release_command." So you CANNOT run SQLite schema migrations in a release command — they must run at app startup, before the FastAPI server accepts traffic. Volumes are also unavailable at build time, so you can't seed the DB into the image either.
- Every deploy stops your only machine and kills any running job. With one machine + one volume, `bluegreen` and `canary` strategies are unavailable (Fly disallows both for machines with attached volumes), so you get `rolling` with a count of 1, which is just stop-then-start. Combined with `kill_timeout` capping at 300s and being "best-effort", a 6-minute pass-2 job WILL be truncated by a deploy. Job resumability is a hard requirement of this architecture, not a nice-to-have.
- `min_machines_running` is a no-op in the configuration you actually want. It "has no effect unless you set auto_stop_machines to 'stop' or 'suspend'". Lots of blog posts recommend `min_machines_running = 1` as the fix for scale-to-zero; with `auto_stop_machines = "off"` it does literally nothing. Don't mistake it for your protection.
- `auto_stop_machines = "suspend"` looks tempting (sub-second resume) but is wrong here on two counts: it still stops your machine mid-job exactly like `"stop"`, and "Suspend is not durable. Fly does not guarantee that a suspended machine will resume." It also caps at 4GB RAM and doesn't support swap. Use `"off"`.
- Size the machine for LibreOffice, not for FastAPI. A headless LibreOffice PDF conversion of a large PPTX plus 4-6 concurrent Anthropic SDK calls holding PDF bytes in memory will not fit in 256MB or 512MB. Start at 2GB and add `swap_size_mb = 512` as an OOM cushion (docs: "Swapping to disk can help avoid out-of-memory crashes on brief spikes in memory use"). An OOM kill is indistinguishable from an autostop from your job's point of view — it kills the work.
- Put ALL scratch I/O on the volume, not the rootfs. Fly documents the ephemeral rootfs as "heavily limited regardless of the Machine type you choose, with the maximum of 2000 IOPs and 8MiB/s bandwidth." LibreOffice temp files, upload spooling, and genanki's .apkg assembly all belong under the mount point. Your volume itself is only 4000 IOPS / 16 MiB/s on shared-cpu-1x/2x, so budget the 200-page PDF handling accordingly.
- Run `fly config validate --strict` in CI. Fly's own blueprint warns: "By default, fly config validate silently accepts unrecognized sections and keys. A typo or outdated section name can pass validation and then do nothing at runtime." Given that a single mistyped `auto_stop_machines` re-enables the job-killing default, this check is load-bearing.
- Let `fly launch` scaffold the app but audit what it writes. Its default `[http_service]` block is `auto_stop_machines = "stop"`, `auto_start_machines = true`, `min_machines_running = 0` — precisely the configuration that kills your background jobs. Also note the first deploy creates exactly one machine because a volume is mounted, which is what you want, but means you have zero redundancy from day one.
- Your daily volume snapshot is not a backup. Fly says so directly: "Daily automatic snapshots may not have your latest data. You should still implement your own backup plan for important data" and "snapshots shouldn't be your primary backup method." For a DB holding stable per-card UUIDs that make re-imports update rather than duplicate Anki notes, losing the DB means every user's future re-import duplicates their whole deck and destroys their scheduling. That's the worst failure mode in this entire design. Back up the SQLite file (`VACUUM INTO` + push offsite) on a schedule, independent of Fly.
- 30-day auto-purge plus a fixed-size volume is a silent bomb. 150MB/job on a 3GB volume is ~20 retained jobs. Configure `auto_extend_size_threshold = 80` with `auto_extend_size_increment` and `auto_extend_size_limit` (Fly warns: "Without these values, the volume won't resize automatically, even if the usage threshold is reached"), and remember you can never shrink it back — you'll pay $0.15/GB/mo forever at the high-water mark. Better: delete uploaded source files as soon as pass 2 finishes rather than holding them 30 days; keep only the generated cards.
- The prompt-caching economics interact badly with restarts. Anthropic's 1-hour cache TTL means a killed-and-resumed job that restarts after the TTL re-pays the full cache-write cost for the document. If you checkpoint per-topic, resume promptly on boot rather than waiting for a user to re-trigger.
- If you put Cloudflare in front of this for a custom domain, note Fly's own warning about 520s from the `TE: trailers` header, and that Cloudflare's own proxy has a 100MB free-plan upload cap that would break your 150MB uploads well before Fly does. Point the custom domain straight at Fly (grey-cloud / DNS-only) unless you have a reason not to.
- There is a 2048-concurrent-connection-per-edge-per-app limit mentioned by Fly staff and not documented in the LB docs. Irrelevant at your scale, but if you ever leak SSE connections (clients that never close), you'll accumulate them — use `type = "requests"` concurrency rather than the `connections` default, and reap dead SSE streams server-side.

## Issues

### BLOCKER

**Nothing maps a regenerated card back to its existing UUID — the whole stable-GUID scheme has no anchor** _(lens: correctness)_

- problem: The design says "stable per-card UUIDs persisted in SQLite and passed to genanki as the note GUID" so that re-import updates in place. But pass 2 is a nondeterministic LLM call. On regeneration, the topic "Glycolysis" comes back with a different number of cards, in a different order, with reworded questions. There is no defined procedure for deciding that regenerated card #3 IS the card that already holds UUID x. Any index-based assignment is actively harmful: if v1 card 3 was "What is the rate-limiting enzyme of glycolysis?" (user has 40 reps, ivl=90) and v2 card 3 is "In which cellular compartment does glycolysis occur?", Anki matches on GUID, replaces the fields, and leaves the card row untouched — so the user's 90-day interval is now attached to a question they have never seen. This is worse than duplicating, because it is silent and corrupts the review data rather than just cluttering it. If instead you mint a fresh UUID per generated card, every regeneration duplicates the entire deck and the design's headline feature does not exist at all.
- fix: Make card identity explicit and content-anchored rather than positional. Persist per card: uuid, topic_path, note_type, and a normalized fingerprint of the question/cloze-source text. On regeneration, include the existing cards for that topic (uuid + question text) in the pass-2 prompt AFTER the cache breakpoint, and require the structured output to return, per card, either an `existing_uuid` it is revising or `"new"`. Server-side, verify each claimed reuse with a similarity check against the stored fingerprint and reject reuse below threshold. Cards not claimed are retired (their UUID is never reissued), not silently reassigned. Never assign UUIDs by list position.

**Per-card note type is LLM-chosen and user-editable, which is the exact input that silently destroys existing notes** _(lens: correctness)_

- problem: The design has pass 1 propose a note type per topic that "the user edits/approves in the UI", and separately specifies "mixed Basic + Cloze note types chosen per card". Concrete trigger: user generates a deck, studies it for two weeks, then reopens the plan, flips topic "Cardiac Cycle" from Basic to Cloze, and regenerates. Every existing card in that topic keeps its UUID but arrives with a different notetype_id. Verified against Anki 26.08: `maybe_update_existing_note` sees `incoming.notetype_id != existing.notetype_id`, calls `log_conflicting`, and the note is neither updated nor added — the import reports conflicting=N, the user's cards keep their stale v1 text, and a junk notetype named "...+" is left in their collection. If the user has ever enabled "Merge note types" (it is sticky once set), Anki instead raises "Cloze note types cannot be merged with regular note types" inside the transaction and the ENTIRE import aborts — nothing is imported at all. Neither outcome surfaces as an error in ai-anki; the app reports success and hands over a file that quietly does nothing.
- fix: Treat note type as immutable per UUID. Persist note_type alongside the UUID at first export and pin it: pass 2 receives the pinned type as a constraint for existing cards and may only choose freely for new ones. If a topic's note type changes, mint new UUIDs for that topic's cards and mark the old ones retired — do not reuse the GUID. Additionally, hard-code both model_ids as app-wide constants (never per-job randomized), freeze their field/template lists, and add a test asserting those lists never change; any future change must allocate a new model_id.

**30-day auto-purge of cards deletes the UUID ledger, so any regeneration after a month duplicates the user's whole deck** _(lens: correctness)_

- problem: The design states "30-day auto-purge of uploads and cards". The UUID→card mapping IS the card record. A user generates a 400-card deck, studies it for six weeks, then uploads an updated lecture PDF and regenerates. The server no longer holds any of the original UUIDs, so it mints 400 new ones. The user imports, and because Anki matches only on GUID with no first-field dedup on the apkg path, they get 800 notes — their original 400 with intact scheduling plus 400 identical-looking new ones at ivl=0. This is the single most user-destructive outcome in the design and it is guaranteed by the retention policy, not by any edge case. It also directly contradicts the stated purpose of persisting UUIDs.
- fix: Split retention: purge uploaded source files and generated .apkg blobs at 30 days, but retain the card ledger (uuid, deck_path, note_type, question fingerprint, tags) indefinitely, or at minimum for years. It is a few hundred bytes per card. Separately, back the SQLite file up off-Fly on a schedule (`VACUUM INTO` plus offsite push) — Fly's daily volume snapshot is explicitly documented as not a backup, and losing this DB has the same effect as the purge.

**The user-editable topic tree cannot reorganise cards that already exist; regeneration leaves stranded cards and a litter of empty decks** _(lens: correctness)_

- problem: The design's core UX is that the user edits the topic tree and it maps onto '::' subdeck names. Verified against Anki 26.08: decks are matched by NAME, and `import_cards` never rewrites an existing card's `did`. Concrete trigger: user regenerates after renaming "Bio::Cell::Mitochondria" to "Bio::Organelles::Mitochondria". The notes' fields update, but every existing card STAYS in Bio::Cell::Mitochondria, while empty Bio::Organelles and Bio::Organelles::Mitochondria decks are created alongside. After two or three plan edits the user's deck list is mostly empty decks with their real cards in the original tree. Worse, when an existing cloze note gains a c2 on regeneration, the new ord=1 card lands in the NEW deck while ord=0 stays in the OLD one — a single note's cards split across two subdecks. The UI will show a reorganisation that Anki will never perform.
- fix: Freeze deck_path per UUID at first export and store it; regeneration always emits the card under its original path regardless of what the plan now says. Carry the mutable topic identity in tags (which ARE replaced wholesale on update and therefore do track the plan). In the UI, grey out or explicitly warn on reparenting existing topics: "cards already exported will stay in their original deck." Topic-tree edits apply fully only to cards that have never been exported.

**No spend ceiling anywhere: one shared password gates unbounded Opus 5 spend** _(lens: cost-and-failure)_

- problem: Auth is a single shared password held by 'a handful of known friends' on a publicly reachable URL. That password ends up in a group chat, or a friend shows the app to someone else. There is no per-job, per-session, or global token budget in the design, and no Anthropic Console spend limit is specified. At the documented Opus 5 rates a single 200-page job is ~$7-10 for the 1-hour cache write plus ~$0.35 per pass-2 topic read plus output at $25/MTok — roughly $15-25 per job. Ten people running five jobs each in an afternoon is a four-figure bill with nothing in the system able to notice or stop it. The page cap is the only limit in the design and it bounds neither tokens nor dollars.
- fix: Four layers. (1) Set a hard monthly spend limit and a low-balance alert on the Anthropic organization as the outer backstop — this is the only control that survives an application bug. (2) Persist input_tokens, cache_creation_input_tokens, cache_read_input_tokens and output_tokens per API call in SQLite, and compute cost from a hardcoded price table. (3) Enforce a per-job token budget checked before pass 1 and re-checked before the pass-2 fan-out, aborting the job when exceeded, plus a rolling 24-hour budget keyed on the session cookie and a global daily ceiling that shuts the worker down. (4) Replace the single shared password with per-user signed invite tokens stored in SQLite so one leak can be revoked without rotating everyone, and so per-user budgets are attributable at all.

**Crash-loop on resume re-pays the 1-hour cache write on every boot** _(lens: cost-and-failure)_

- problem: Jobs must be resumable because Fly SIGKILLs the machine on every deploy, `fly secrets set`, scale change, host migration and OOM. If a job hits a deterministic crash after pass 2 begins — an unsanitised topic name raising ValueError in genanki's tag validator, an OOM during an image-heavy LibreOffice conversion, a parse error on a truncated structured output — the boot scan finds the job 'running', resumes it, crashes again, and Fly restarts the machine. Each iteration re-establishes the cached document prefix at 2x base input: ~$7 per cycle on a 700K-token document, and a fast crash can cycle several times a minute. Nothing in the design bounds the number of resume attempts.
- fix: Persist `attempt_count` and `last_attempt_at` on the job row and increment `attempt_count` in a committed transaction BEFORE the first Anthropic call of any resume, not after success. Refuse to resume at attempt_count >= 3 and move the job to a terminal `dead` state that requires an explicit human action to clear. Enforce a minimum 60s backoff between resumes, and have the boot scan mark orphaned jobs `interrupted` (user-resumable) rather than auto-resuming when the process has restarted more than twice in the last hour.

**The 200-page cap is measured on a quantity that is unknowable pre-conversion and does not predict tokens** _(lens: cost-and-failure)_

- problem: Pages do not exist for half the accepted inputs and do not correlate with cost. DOCX has no page count until LibreOffice lays it out (a 40-section fixture rendered to 80 pages). Images and XLSX have no pages at all. And a PDF page costs 1,500-3,000 text tokens PLUS up to 4,784 visual tokens on Opus 5's high-resolution tier, because Claude renders every page as both text and image. A student uploads 200 pages of scanned lecture slides: that is roughly 1.2-1.5M tokens, over the 1M context window. The user waits through upload, LibreOffice conversion, a Files API upload, and then pass 1 returns a 400 — after all the ingestion cost was spent. A job that squeaks under 1M still costs about double what any text-only page estimate predicts.
- fix: Make the admission gate `client.messages.count_tokens()` run over the exact assembled document blocks (referenced by file_id, so the 32MB request limit does not apply), executed after LibreOffice conversion and XLSX extraction and before pass 1. Reject above ~700K input tokens so there is headroom for max_tokens, since input + max_tokens must fit inside 1M. Keep a page count only as a cheap pre-filter computed with pypdf after conversion, and stop advertising '200 pages' as the user-facing contract — show the measured token count and the resulting dollar estimate instead.

**A whole-job retry re-pays for every already-completed topic and duplicates cards** _(lens: cost-and-failure)_

- problem: Pass 2 is N independent calls and at least one will realistically fail: a 429 during fan-out, an `overloaded_error`, a safety refusal, or JSON truncated at max_tokens. If failure marks the job failed and the UI offers a single 'Retry' button, the obvious implementation re-fires all N topics — on a 15-topic job that is 15 more document cache reads plus 15 more completions at $25/MTok output to fix one broken topic. Worse for state: if the retried topics mint fresh card UUIDs, the user's next .apkg import gets both generations as separate notes, because Anki's importer matches on GUID only and does no first-field dedup.
- fix: Model pass 2 as one SQLite row per (job_id, topic_id) carrying status (pending/running/done/failed/dead), attempt_count, and the persisted card payload. Retry selects only rows with status IN (pending, failed) and attempt_count below the cap. Write each topic's result in a single transaction that first DELETEs any prior attempt's card rows for that (job_id, topic_id), so a retry replaces rather than accumulates. Derive card UUIDs deterministically from (deck lineage id, topic id, ordinal) rather than random uuid4 per attempt, so a replacement attempt reuses the same GUIDs and updates the user's existing notes in place.

**The user approves a plan, then receives 300 cards they have never seen, straight into their real collection** _(lens: product-and-ux)_

- problem: The only human checkpoint in the design is the deck plan (topics, counts, note types). Concrete scenario: I upload three lecture PDFs, spend two minutes tweaking a 15-topic plan, click Approve, wait four minutes, and download an .apkg containing ~280 cards whose text I have never read. I import it into my 14,000-note collection. Card 41 asserts that the Krebs cycle yields 36 ATP because the 2009 slide deck said so; card 112 is a cloze with the entire sentence deleted; card 190 is a near-duplicate of card 33. I find out weeks later, mid-review, one card at a time. Unwinding is worse than never importing: I can undo the import only if I notice immediately, and after that I am hand-deleting notes out of a live collection. Every downstream decision in this design is also frozen at first export — deck path, note type, and GUID all become immutable the moment those cards land — so the one moment when corrections are cheap is the moment the design gives the user no visibility.
- fix: Add a card review screen between pass 2 and .apkg build. Cards stream in per topic as each parallel call lands; each card shows rendered front and back (cloze rendered, not raw markup), its topic, and accept / edit / reject controls, with bulk reject-by-topic and a 'reject all cards under N characters' style filter. Nothing reaches the .apkg until it is accepted. Also tag every card with the job id (e.g. aianki::job::<uuid>) so a bad batch can be found and mass-deleted in Anki with one search, and print that search string on the download page.

**Regenerating silently destroys the user's own edits, hand tags, and Anki's leech/marked flags** _(lens: product-and-ux)_

- problem: Update-in-place is gated on IF_NEWER, and a regenerated package always has a newer note mtime, so the file always wins. Concrete scenario: I import the deck, then spend an evening in Anki fixing 30 cards — correcting a hallucinated answer, adding a mnemonic to the Back Extra, adding my own tag 'exam::june'. Six weeks later I add lecture 12 to the same job and regenerate. The new .apkg re-exports all 280 notes, including the 250 whose content did not change at all. Every one of my 30 edits is overwritten with the model's original text. All hand tags are replaced wholesale, and so are Anki's own 'leech' and 'marked' tags — leech in particular is a scheduler signal I have been accumulating for weeks. Coloured flags survive, tags do not, and nothing in the UI hints at that asymmetry. The user experiences this as the app eating their work with no warning and no diff.
- fix: Only export notes that actually changed. Store the last-exported field text per card UUID in SQLite; if pass 2 produces byte-identical output for a card, omit it from the package entirely — an omitted note is untouched, so its edits, tags, leech state and scheduling all survive automatically. This alone makes the typical regeneration non-destructive. On top of that: (a) show a pre-download diff screen — 'this file will update 12 notes, add 45, and leave 223 untouched', with the 12 listed and individually skippable; (b) preserve the user's tags by re-emitting the tags you last wrote plus nothing else, and state plainly on the download page that hand-added tags on updated notes are replaced (use flags instead); (c) default the regenerate action to 'add new cards only' and make 'update existing cards' the explicit opt-in.

**Parallel per-topic calls each see the whole document, so overlapping topics generate the same card twice** _(lens: product-and-ux)_

- problem: Pass 2 fires one call per topic, each with the full corpus in context and no knowledge of what the other calls are producing, and Anki dedups only on GUID — two notes with identical fronts import as two separate notes. Concrete scenario: I upload the lecture slides, the textbook chapter, and my own notes for the same neurophysiology unit (the exact multi-file case this app is for). Pass 1 produces topics 'Resting Membrane Potential' and 'Ion Channels'. Both calls see the same three documents, both generate 'What is the resting membrane potential of a typical neuron? / about −70 mV', in slightly different wording. Across 15 overlapping topics this is not an edge case, it is the normal outcome — I end up reviewing the same fact three times forever, in three different subdecks, with FSRS treating them as independent items. Anki's Find Duplicates only catches exact first-field matches on the same notetype, so the paraphrased ones stay invisible.
- fix: Make pass 1 partition the material, not just name it. Have the deck plan carry, per topic, an explicit list of the specific claims/points that topic owns, and make those lists disjoint; pass 2 for topic T is instructed to generate cards only for T's assigned points and is given the sibling topic titles as explicit exclusions. Then add a cheap post-generation dedup: normalize fronts (strip HTML, lowercase, collapse whitespace) for exact matches, plus one final Claude call over the list of all generated fronts asking it to group semantic duplicates, keeping the instance in the most specific topic. Surface the collapsed duplicates in the review screen rather than deleting silently. Separately, tell the user on the download page to run Notes > Find Duplicates after import to catch overlap with cards they already had.

**Editing the topic tree does nothing after the first export, and leaves a litter of empty decks** _(lens: product-and-ux)_

- problem: Anki matches decks by name and never rewrites an existing card's deck on import, so deck placement is write-once per card. Concrete scenario: my first export puts cards under 'Biology::Lecture 7::Glycolysis' because pass 1 named topics after slide titles. I then use the plan editor — the headline feature — to reorganise into 'Biology::Metabolism::Glycolysis' and regenerate. Result: the field text of my existing cards updates, the cards themselves stay in Biology::Lecture 7, and Anki additionally creates empty Biology::Metabolism and Biology::Metabolism::Glycolysis decks. My deck list now has both trees, one full and one empty. Worse, any note that gained a new cloze ordinal in the regeneration has its old card in the old deck and its new card in the new deck — one note, two decks. From the user's side the app looks broken and the plan editor looks like a lie.
- fix: Freeze the deck path per card UUID in SQLite at first export. In the plan editor, render already-exported topics' paths as locked with an inline explanation ('Anki can't move cards that already exist — rename the deck inside Anki instead, which does move them correctly'), and offer a one-click copy of the exact old-name → new-name rename for the user to perform in Anki. Let topic-tree edits affect only cards that have not yet been exported. Carry live, mutable topic identity in tags (which do get replaced on update) rather than in the deck path, so a reorganised plan is still reflected somewhere the user can search on.

**No rule for mapping regenerated cards onto existing card UUIDs — the headline feature has no mechanism** _(lens: completeness)_

- problem: The design's central promise is that re-importing a regenerated deck updates notes in place and preserves scheduling, via stable per-card UUIDs persisted in SQLite. But nothing in the design says how a card produced by a *later* pass-2 run is matched to a UUID issued by an *earlier* run. Pass 2 fires per topic and returns a fresh array of card objects; there is no key on those objects tying them to prior cards. Scenario: user generates a deck (30 cards, 30 UUIDs stored), studies for two weeks, uploads a corrected lecture PDF and regenerates. Pass 2 returns 31 similar-but-not-identical cards. With no matching rule the app either mints 31 new UUIDs (every note duplicates in Anki, scheduling lost, the entire feature is inert) or blindly zips new cards onto old UUIDs by array index (card 7's review history silently attaches to an unrelated fact). Content-hash matching is explicitly ruled out by the verification (genanki's default guid_for hashes fields, and the whole point of passing guid= is to survive content edits).
- fix: Decide and specify the identity mechanism before any code. Concretely: (a) introduce a `deck` entity in SQLite distinct from `job`, so regeneration is 'job N against deck D' rather than a fresh job; (b) define the per-card slot key — the workable one is `(deck_id, topic_path, slot_index)` where pass 2 is prompted with the existing cards for that topic and asked to return them in order with an explicit `existing_card_id` field (null for new cards), and the server validates that every returned existing_card_id belongs to that topic; (c) write down what happens for cards the model omits (retired, keep UUID reserved, never reuse) and cards it adds (new UUID appended). Add a test that regenerates a deck twice and asserts UUID stability for unchanged slots.

**30-day auto-purge destroys the UUID ledger that makes re-import non-destructive** _(lens: completeness)_

- problem: The design states '30-day auto-purge of uploads and cards' and, separately, that per-card UUIDs are persisted in SQLite so re-import updates in place. These contradict. Scenario: a user generates a deck in January, studies it in Anki all quarter, comes back in April and regenerates from the same documents. The card rows — and therefore the UUIDs — were purged on day 30, so every note re-imports as new: their whole deck duplicates and every card's review history is orphaned. This is the single worst user-visible failure in the design and it is caused by two agreed bullets that were never reconciled. It is also not recoverable after the fact.
- fix: Split retention by data class and write it down: purge *uploaded source files* (the bulk of the volume, and the actual disk pressure) on a schedule, but retain card rows — UUID, deck path, note type, topic, and last-exported field text — indefinitely, or at minimum keep a tombstone table of (deck_id, card_uuid, deck_path, notetype) that is never purged. It is a few hundred bytes per card. Then decide and state what regeneration does when the sources are gone (require re-upload, and match the new job to the existing deck lineage explicitly).

**Deck path and note type mutability is undecided, and the agreed feature set actively invites both silent-failure modes** _(lens: completeness)_

- problem: Verification established two hard constraints: (1) a note whose notetype_id changes between imports is silently dropped (conflicting=1, old content retained, junk notetype left behind) or, with merge_notetypes on, aborts the entire import with a BackendError; (2) an existing card never moves decks, so a reorganised topic tree updates fields but leaves cards behind and litters the collection with empty subdecks. The agreed design contains both triggers as headline features: 'mixed Basic + Cloze note types chosen per card' (pass 2 re-picks per card, per run) and 'user edits/approves the topic tree' (which is the deck path). No decision has been recorded either way, so an implementer reaching this ticket has to invent policy or will ship the failure.
- fix: Record two explicit rules. Note type: persist `notetype` alongside each card UUID and PIN it — pass 2 is told the note type for an existing slot and may not change it; a genuine Basic↔Cloze change retires the old UUID and mints a new one, with the UI stating the old card must be deleted manually in Anki. Deck path: adopt the option the verification says actually works — freeze `deck_path` per card UUID at first export, make the editable topic tree affect only *new* cards and the `topic::` tag (tags ARE replaced on update, so they track the plan), and show 'existing cards stay in their original deck' in the regenerate UI. Also add a startup assertion that the two model_ids are hardcoded constants and a test that their field/template lists are unchanged.

**Auth is one line of the design and has no session, rate-limit, CSRF, or spend-authorization model** _(lens: completeness)_

- problem: 'Single shared password in an env var, HTTP-only session cookie' leaves every security decision unmade for a publicly-reachable app that holds other people's documents and fronts an unmetered Anthropic API key. Undefined: whether the cookie carries a signed token or an opaque session id in SQLite; session lifetime and revocation; cookie Secure/SameSite/Path attributes; what invalidates sessions when the password rotates; login attempt rate limiting or lockout; and CSRF protection on the POST endpoints that spawn jobs. Scenario: a bot finds the .fly.dev hostname and brute-forces a weak shared password at 50 req/s with no lockout, then submits 200-page jobs — each one is $15-25 of Opus 5 spend with no per-job or global budget cap and no way to cancel. There is also no defined signing secret: if the session cookie is signed with a value derived from the password, rotating the password after a leak must log everyone out, and that behaviour is unspecified.
- fix: Specify: opaque 128-bit random session id stored in SQLite with an absolute expiry (e.g. 30 days) and a `sessions` table you can truncate to force logout; cookie flags `HttpOnly; Secure; SameSite=Lax; Path=/`; constant-time password comparison; a per-IP login rate limit (e.g. 5 attempts / 15 min, backed by the same SQLite) with a fixed delay on failure; SameSite=Lax plus a same-origin `Origin`/`Sec-Fetch-Site` check on all mutating endpoints in place of tokens. Separately specify a spend guard: a per-job token ceiling enforced at admission via count_tokens, a rolling 30-day org spend cap read from persisted usage rows, and a hard kill switch env var.

**No job state machine, no crash-safe resume — and Fly kills the machine on every deploy** _(lens: completeness)_

- problem: The design says 'in-process background worker' and nothing else. Fly verification established that deploys, host migrations, OOM kills, and `fly secrets set` all SIGTERM the single machine, with kill_timeout capped at 300s and documented as best-effort; a 15-topic pass-2 run exceeds that. Scenario: you deploy a frontend tweak while a friend's job is on topic 9 of 15. The machine stops, the process dies, and on restart there is a row in SQLite that says 'running' with no worker behind it. The UI's SSE stream reconnects to a job that will never emit another event and never completes — no timeout, no failure, no resume. Resuming also matters for cost: an interrupted job restarted more than an hour later re-pays the full 1-hour cache write on the whole document.
- fix: Enumerate job states explicitly (e.g. uploaded → converting → planning → plan_ready → generating → assembling → complete / failed / interrupted / cancelled) and per-topic states within `generating`, persisted transactionally as each topic completes. On boot, scan for jobs in a non-terminal state with no live worker and either auto-resume the incomplete topics or mark them `interrupted` with a Resume button. Set `kill_signal = "SIGTERM"`, `kill_timeout = "300s"`, use the exec-form CMD so the app is PID 1, install an asyncio SIGTERM handler that stops accepting new topics and checkpoints, and set `auto_stop_machines = "off"` / `auto_start_machines = true`. Add `fly config validate --strict` to CI.

### MAJOR

**Pass 2 cannot share pass 1's cached prefix as designed, and the failure mode is 4-6 simultaneous full-price 1-hour cache WRITES** _(lens: correctness)_

- problem: Pass 2 must know the approved deck plan (to avoid overlapping topics) and must constrain output to a card schema rather than a plan schema. The natural implementation puts "Here is the approved plan… now generate cards for topic X" in the system prompt and swaps `output_config.format`. Cache render order is tools → system → messages, and the documents live in `messages` — the LAST tier. So a different system prompt guarantees the document blocks can never match, and whether `output_config.format` is rendered into the prefix is undocumented and untested. Because all N pass-2 calls then fan out concurrently against a cold entry, and a cache entry only becomes readable after the first response begins, every one of them independently pays cache_creation at the 1h rate (2x base = $10/MTok). On a ~700K-token job that is roughly $7 per call — about $42 for a 6-wide fan-out instead of ~$2 in reads, with no error raised anywhere. `effort` and the thinking config are also rendered into the prompt and always invalidate message blocks, so any per-pass tuning of those has the same effect.
- fix: Lock a single shared prefix used byte-identically by both passes: one generic pass-agnostic system prompt, identical tools/tool_choice, identical explicit `effort`, identical explicit thinking config, then the document blocks with `cache_control {type: ephemeral, ttl: "1h"}` on the LAST document block. Every pass-specific instruction — including the approved plan and the topic name — goes in a text block AFTER the breakpoint. Decide structured-outputs usage empirically before building: run pass 1 with `output_config.format` and pass 2 with a different schema and assert `cache_read_input_tokens > 0`; if it is zero, use the same schema shape (or none) on both. Persist `cache_read_input_tokens` / `cache_creation_input_tokens` per call in SQLite and add a test asserting pass-2 calls 2..N read and do not create — a silent regression here is a ~20x cost multiplier with no symptom.

**No cache priming step and no handling of the human approval gap, so the common path is a cold parallel fan-out** _(lens: correctness)_

- problem: The design places a human editing/approval step between pass 1 and pass 2 and then fires 4-6 calls in parallel. Trigger: the user generates a plan at 5pm, closes the laptop, approves it at 9pm. The 1-hour entry is long gone. `asyncio.gather` over the topics then sends all 6 into a cold cache simultaneously and each pays the full write, exactly as in the previous issue — even when prefixes are perfectly identical. The same happens on the resume path: a deploy or OOM kills the job mid-fan-out, the worker restarts, and it re-fans-out in parallel into whatever cache state exists.
- fix: Make the fan-out a two-phase operation, never a bare gather. On approve: if the last cache write was more than ~45 minutes ago, send a priming request first (a plain non-streaming `max_tokens: 0` request carrying the identical prefix — note this is rejected alongside `stream: true`, `output_config.format`, and forced `tool_choice`, so the primer must be a plain request), await it, then fan out. Otherwise fire exactly one topic call, await it completing, then fan out the rest. Show the plan's cache freshness in the UI, and refresh the entry cheaply while the user deliberates (cache hits refresh the TTL for free). Apply the same priming rule on worker restart/resume.

**The obvious cloze validator lets through markers that genanki turns into zero-card notes** _(lens: correctness)_

- problem: genanki 0.13.1's `_cloze_cards` contains `if card_ords == {}` comparing a set to an empty dict, which is always False, so a cloze note with no matched ordinals yields NO cards — silently, with no warning. Its matching regex is `{{c(\d+)::.+?}}`. I verified concretely: `{{c1::}}` (model produced a marker but omitted the answer) matches the natural validator `\{\{c\d+::` yet yields `cards == []`; `{{ c1::x }}` and `{{C1::x}}` fail both. Trigger: on a 400-card deck, Claude emits a handful of these; the app reports success, the .apkg imports without error, and those notes land in the collection with zero cards attached. The user never sees the content, and nothing in the pipeline flags it.
- fix: Validate with genanki's own regex, not a looser one: require `re.findall(r'{{c(\d+)::.+?}}', text)` to be non-empty, and additionally require ordinals to start at 1 and be contiguous. Anything failing downgrades to BASIC_MODEL (with a new UUID, per the note-type immutability rule) or is dropped with a visible warning in the job report. Independently, vendor-patch the `card_ords == {}` line to `if not card_ords:` — the fix exists on main but has never been released. Assert `len(note.cards) > 0` for every note before adding it to the deck.

**'::' inside a cloze answer is silently reinterpreted as Anki's hint delimiter and hides the answer** _(lens: correctness)_

- problem: Anki's cloze syntax is `{{cN::answer::hint}}`. The design generates study material that frequently contains '::' — Anki deck paths, C++ scope resolution, Rust/PHP namespaces are all plausible study content, and the app's own topic paths use '::'. Trigger: Claude emits `{{c1::std::vector}}`. genanki's regex matches and produces a card; Anki renders the answer as "std" with hint "vector". The card is wrong and the failure is invisible — it imports cleanly, produces the right card count, and only a human reading the card notices. The reverse also bites: the pipeline's HTML-escaping step must not run over cloze markup (escaping cannot break braces, but escaping applied after marker insertion to a field that already contains `<img>` you injected will corrupt it), so the ordering of escape vs. cloze-wrap vs. img-injection has to be pinned.
- fix: After parsing pass-2 output, scan every cloze field for '::' occurrences beyond the marker's own delimiter and either reject the card back to the model, or escape the inner colons. Add a positive unit test with `{{c1::std::vector}}`. Separately, fix the field pipeline order explicitly: html.escape() the model's plain prose FIRST, then insert cloze markers, then inject any `<img>` tags — and add a test that a field containing `a<b && c>d` survives, since genanki's `_check_invalid_html_tags_in_fields` does not warn on it.

**Cloze ordinal drift across regenerations attaches review history to the wrong content and leaves blank cards** _(lens: correctness)_

- problem: Anki updates notes without touching cards. Trigger A: a note is regenerated from `{{c1::pyruvate}} … {{c2::NADH}}` to `{{c1::NADH}} … {{c2::pyruvate}}` — a completely benign LLM reordering. Card ord=0 keeps its 60-day interval but now tests NADH; ord=1 keeps its lapse history but now tests pyruvate. Nothing errors. Trigger B: regeneration drops c2 entirely. Verified: the ord=1 card remains in the collection with its full review history and now renders blank; `get_empty_cards()` reports it but only the user manually running Tools > Empty Cards deletes it. Since pass 2 has no memory of prior ordinals, both triggers are the default behaviour, not edge cases.
- fix: Persist the ordinal→answer-text mapping per UUID. On regeneration, pass the existing ordinal assignments to pass 2 after the breakpoint and re-derive ordinals server-side by matching answer text, never by the model's numbering. Ordinals may only grow: never renumber, never reuse a retired ordinal. If a deletion is genuinely required, mint a new UUID for the note and retire the old one rather than shrinking the ordinal set, and tell the user in the download page that removed cards need Tools > Empty Cards.

**A tag containing a space raises ValueError and kills the entire deck build after all Claude spend** _(lens: correctness)_

- problem: The design specifies "tags for topic/difficulty/source page" and the topic names come from an LLM. genanki's `_TagList._validate_tag` raises rather than warning — I confirmed `n.tags.append('topic::Cell Biology')` raises `ValueError: Tag "topic::Cell Biology" contains a space; this is not allowed!`. "source page 12" raises identically. Trigger: any deck plan with a two-word topic name, which is essentially all of them. The exception fires at the final assembly step, after both passes have completed and the job has cost real money, and takes down the whole build rather than one card. Tags are also replaced wholesale on update, so any `marked`/`leech` tag or hand-added user tag is wiped on every regeneration.
- fix: Sanitize at the boundary with `re.sub(r'\s+', '_', tag)` on every tag before it reaches genanki, and unit-test it with an LLM-realistic topic name. Use `source_page::12` / `difficulty::hard` forms. Wrap final assembly so that a per-card failure degrades that card rather than the job. Document the tag-replacement behaviour in the UI, or round-trip the user's existing tags.

**Nothing bounds the deck plan, so an absurd plan is executed as written — cost blowout plus truncated structured output** _(lens: correctness)_

- problem: Structured outputs cannot enforce `maximum`, `minimum`, or `maxItems`, and the Python SDK silently strips `Field(ge=1, le=30)` into an advisory description. Trigger A: a 200-page textbook makes pass 1 return 60 topics × 40 cards = 2,400 cards. The worker dutifully fires 60 pass-2 calls; at ~700K cached tokens each that is ~$21 in reads alone, plus thinking and output at $25/MTok, on an app where the user was shown no estimate and there is no per-job budget. Trigger B: a single topic proposes 80 cards. `max_tokens` (which includes Opus 5's on-by-default thinking) is exhausted mid-object, the structured JSON is truncated, `messages.parse` throws, and the topic is lost after being paid for in full. Trigger C: the plan proposes 0 topics or 0 cards and the app produces an empty .apkg that Anki imports as nothing. Trigger D: a deep generated path exceeds Anki's hard limit of 11 nesting levels and the import fails outright.
- fix: Clamp everything in Python after parsing, not in the schema: cap topics per job, cap cards per topic (~25), cap total cards per job, and clamp deck path depth to <=8 components. Reject empty plans. Show the user the clamped plan and a cost estimate before they approve, and enforce a hard per-job token budget in the worker. For topics whose approved count exceeds what fits in one response, split into multiple pass-2 calls over disjoint card ranges rather than raising max_tokens. Note that any max_tokens above 21,333 forces the SDK into streaming mode, so the worker must use `client.messages.stream(...).get_final_message()` — a plain `create()` will fail client-side.

**The 200-page cap does not bound the context window, and for DOCX/PPTX the page count is unknowable before conversion** _(lens: correctness)_

- problem: Claude converts each PDF page to BOTH extracted text (~1,500-3,000 tokens) AND a page image (up to 4,784 visual tokens on Opus 5's high-res tier), so 200 pages is roughly 600K-1.5M input tokens. The upper half does not fit in the 1M window. Trigger: a user uploads 200 pages of dense scanned lecture notes — exactly the case the design says it supports via Claude vision instead of OCR. Pass 1 fails at request time, after upload, after LibreOffice conversion, with an opaque API error. Compounding this, a DOCX has no page count until it is laid out: I have measured a 40-section DOCX rendering to 80 PDF pages, so the cap cannot be checked at upload and font substitution can shift pagination between image rebuilds.
- fix: Admission-control on tokens, not pages or megabytes. After conversion, assemble the exact document blocks and call `client.messages.count_tokens()`; reject above a ~700K ceiling that leaves room for thinking and output. Count PDF pages with pypdf only AFTER conversion. Also verify LibreOffice output by file existence and non-zero size, never by exit code — a truncated DOCX exits 0 with no PDF, and a profile clash exits 1 with no message — and sanity-check the resulting PDF has real content, since a 0-byte .docx converts "successfully" into blank pages you then pay Opus to read.

**The source-page tag as designed is a hard 400, and enabling citations to fix it destroys the document cache** _(lens: correctness)_

- problem: Citations and structured outputs are mutually exclusive: enabling `citations: {enabled: true}` on a document block while also sending `output_config.format` returns a 400. Trigger: pass 2 uses structured outputs to return cards AND enables citations to populate the per-card source-page tag — every pass-2 call fails immediately. Turning citations on for pass 2 only is also self-defeating: the citations toggle invalidates system and message blocks, so the document cache written by pass 1 can never be read. And for the scanned-PDF case the design explicitly supports, citations do not work at all — image citations are unsupported, so scans are simply not citable.
- fix: Drop citations entirely. Have the model emit `source_page` as an integer field inside the card schema, clamp it to the document's real page range, and label the tag as model-reported rather than verified. Do not surface it as authoritative page provenance in the UI. Keep the citations toggle identical (off) across both passes so the cached prefix survives.

**Parallel per-topic generation with the full document in context reliably produces duplicate cards, and Anki will not dedup them** _(lens: correctness)_

- problem: Every pass-2 call sees the entire document and is told only which topic to write for. Trigger: topics "Cell Structure" and "Cellular Respiration" both cover mitochondria; the two parallel calls independently generate "What do mitochondria produce?". Each gets its own UUID, so Anki imports both as separate notes — the apkg import path matches ONLY on GUID and does no first-field dedup (genanki even writes csum=0). The user gets near-identical cards in two subdecks, and Anki's browser later flags them as duplicates with no way to know which one carries their review history. Because the calls are concurrent, no call can see what the others produced.
- fix: Add a server-side dedup pass between pass 2 and .apkg assembly, before UUIDs are assigned: normalize question text, hash/embed, and collapse near-duplicates, keeping the one in the topic whose plan claims the concept. Additionally, give each pass-2 call the full approved topic list (after the breakpoint) with an explicit boundary instruction naming which adjacent topics own overlapping concepts. Do not rely on Anki to catch any of this.

**Resuming a job fans out cold and pays N simultaneous cache writes — worse than not caching at all** _(lens: cost-and-failure)_

- problem: Anthropic's docs are explicit that a cache entry only becomes readable after the first response begins, so concurrent misses each independently pay cache_creation, which at the 1-hour TTL is 2x base input — strictly worse than an uncached read at 1x. A deploy lands at minute 3 of pass 2; on boot the worker resumes the 9 remaining topics with a bare `asyncio.gather` at concurrency 6. If the entry is gone (more than an hour elapsed, or the job was interrupted long enough), those 6 concurrent calls each write ~700K tokens: about $42 instead of the ~$8.75 a properly sequenced run costs. The design's 'fire one first, then fan out' sequencing exists only in the happy path; the resume path is where it will be forgotten.
- fix: Make prime-then-fan-out a single function used by both fresh runs and resumes, with no other code path able to start pass-2 calls. On any entry into pass 2, run exactly one topic call to completion first, inspect its `usage`: if `cache_read_input_tokens` is 0 you have just paid the write and the rest may now read; only then release the semaphore for the remaining topics. Persist `cache_prefix_sha256` and `cache_last_hit_at` on the job so the resume path can log whether it expects a hit, and alarm when it does not get one.

**The pre-generation estimate is shown before the variable that dominates cost is known** _(lens: cost-and-failure)_

- problem: Total spend is dominated by (number of approved pass-2 topics) x (document cache read + completion). Topic count is produced by pass 1 and then edited upward by the user, so any estimate shown at upload time is a guess. Structured outputs cannot enforce `maxItems`, and the Python SDK silently strips `Field(le=...)` into a description, so nothing stops pass 1 proposing 60 topics on a 200-page textbook and nothing stops the user raising proposed_card_count to 100 per topic in the editor. A job estimated at '$8' at upload then spends 60 x $0.35 in reads plus 60 completions, and the user was never shown the real number at the moment they committed.
- fix: Two estimates and two confirmations. Estimate 1 before pass 1, derived from count_tokens: cache write + one completion, which is all that is knowable. Estimate 2 rendered on the plan-approval screen, recomputed from the actual approved topic count and card counts, displayed as a range, with the Approve button disabled until it is acknowledged. Independently, clamp the parsed plan in Python before it reaches the UI: hard-cap topics (e.g. 25), cards per topic, total cards, and tree depth at 11 (Anki's hard limit); reject or truncate server-side rather than trusting the schema, and re-clamp the user-edited plan on submit.

**Six-way fan-out reserves output rate limit from max_tokens and will 429 mid-job, and SDK auto-retry can double-bill a topic** _(lens: cost-and-failure)_

- problem: Opus 5 allows 128K output and thinking counts against max_tokens, so the natural move is a roomy per-topic budget. Output-token rate limit is reserved from the requested max_tokens at request start, so six concurrent calls at max_tokens=64,000 reserve 384K output tokens instantly and will 429 on all but the highest tiers — after the document cache write is already paid. Separately, the Anthropic SDK retries by default; a client-side timeout on a long streamed call re-sends a request that is still generating server-side, so you are billed for the topic twice and may commit two card sets for it.
- fix: Size max_tokens per topic from the approved card count (roughly cards x ~400 tokens plus a measured thinking allowance) rather than a blanket 64K. Cap concurrency with a semaphore tuned to your actual ITPM/OTPM tier, and note that cache reads do not count against the input rate limit, so the binding constraint is output, not input. Honour `retry-after` on 429 with jitter and treat 429 as 'requeue this topic', never 'fail the job'. Construct the SDK client with `max_retries=0` and implement retry yourself at the topic level so every retry is a counted, logged, budget-checked event; use a generous client timeout with `client.messages.stream(...)` so a slow call is never silently re-issued.

**stop_reason is not handled: truncation and refusals both burn full output cost and then loop** _(lens: cost-and-failure)_

- problem: Two realistic pass-2 endings are unaddressed. (a) `stop_reason: max_tokens` — thinking is on by default on Opus 5 and shares the max_tokens budget, so a 30-card topic can exhaust it mid-JSON; with structured outputs you get an unparseable truncated object having paid for every output token at $25/MTok. (b) refusal — a study deck built from a pharmacology module, a forensic pathology course, or an offensive-security syllabus can trip a safety classifier deterministically. In both cases a generic 'retry failed topics' loop re-issues the identical request and gets the identical failure, paying the full read plus a full truncated completion on every attempt.
- fix: Branch explicitly on `stop_reason` and never treat all failures the same. On `max_tokens`, retry at most once with a larger budget AND a reduced requested card count, then mark the topic `dead` with a user-visible 'this topic is too large, split it in the plan' message. On a refusal stop_reason, do not retry at all — mark `dead` immediately and surface the reason, since the retry is guaranteed to cost money and fail. Cap attempts per topic at 2 in the DB, and make the retry endpoint refuse rows already in `dead`.

**SIGTERM cancels in-flight streams, discarding completions you have already paid for** _(lens: cost-and-failure)_

- problem: Fly sends SIGTERM then SIGKILL after kill_timeout (max 300s, and documented as best-effort) on every deploy, `fly secrets set`, scale change and host migration. The idiomatic asyncio shutdown — cancel the TaskGroup, close the client — aborts up to six streams that may each be 80% through a completion costing a dollar or more. Those output tokens are billed whether or not you keep the bytes; the cards are lost; the resumed job regenerates them from scratch and pays again.
- fix: On SIGTERM, immediately stop dispatching new topics but let in-flight calls run to completion inside an internal deadline set ~30s below kill_timeout, persisting each topic's cards to SQLite the instant its stream ends. Set `kill_signal = "SIGTERM"` and `kill_timeout = "300s"` in fly.toml, and use the exec form of CMD (or `exec` in the entrypoint) so the app is actually PID 1 and receives the signal. Persist partial streamed text for any call that does get cut, so it can be inspected rather than silently dropped. Always use `fly secrets set --stage` followed by a deliberate deploy, so an API key rotation never restarts the machine mid-job.

**A failed job discards the topics that already succeeded** _(lens: cost-and-failure)_

- problem: If the job's terminal state is binary — complete or failed — then 12 successful topics representing ~$20 of spend are thrown away because topics 13, 14 and 15 hit a 429 or a refusal, and the user's only affordance is to run the whole job again. This is the same money burned twice, and it compounds the whole-job-retry problem.
- fix: Never gate the deliverable on completeness. Persist cards per topic as each call returns, always allow .apkg download of whatever exists, and show per-topic status (done / failed / dead) with a per-topic retry control. A partial deck is a correct deck in Anki terms: the missing topics simply add notes on a later import, and because GUIDs are stable the second import merges into the same collection without duplicating anything.

**Pinning effort and thinking for cache-correctness removes the only cost lever, and thinking spend is invisible** _(lens: cost-and-failure)_

- problem: `output_config.effort` and the thinking configuration are rendered into the prompt and always invalidate message-level cache entries, so pass 1 and pass 2 must use byte-identical values or the document cache is dead. That forecloses the obvious optimisation of planning at `high` and generating at `medium`. Meanwhile effort defaults to `high`, thinking is on by default on Opus 5, thinking tokens are billed as output at $25/MTok, and `display` defaults to `omitted` so the volume is invisible in the response. A 15-topic job can plausibly spend more on unseen reasoning than on the cards it produces, and nothing in the design measures it.
- fix: Define one `MODEL_CALL_CONFIG` constant (model id, effort, thinking config, tools, tool_choice) imported by both passes, with a test asserting both request builders derive from it — a divergence here is a silent ~10x cost regression, not a visible error. Choose the effort level once from a measured spike comparing deck quality at `medium` vs `high` on a fixed corpus, rather than by intuition. Record output_tokens per call in SQLite and show a thinking-vs-cards token breakdown on the job detail page so a regression is visible. Do not reach for `thinking: {type: "disabled"}` as the cost lever — it 400s at effort xhigh/max and degrades output; lowering effort is the documented lever.

**Unverified assumption: structured outputs may break the shared cache prefix, and the documented pre-warm is incompatible with it** _(lens: cost-and-failure)_

- problem: The entire cost model rests on pass 2 reading a prefix written by pass 1. Pass 1 will use `output_config.format` for the deck plan; whether that parameter is rendered ahead of the message blocks is undocumented and absent from the invalidation table. If it is rendered into the prefix and pass 2 uses a different schema (or none), every pass-2 call misses and the job costs roughly 10x the estimate — with no error raised, no exception, and nothing in the UI to indicate it. Separately, the documented cache-warming trick (`max_tokens: 0`) is rejected when `output_config.format` is set, so the intended mitigation for a plan-approval gap does not exist in the shape this design needs.
- fix: Measure this before writing the worker. Spike it: pass 1 with `output_config.format` and a 1h breakpoint on the last document block, then a pass-2-shaped call, and assert `cache_read_input_tokens > 0`. If it is zero, use the same `output_config.format` schema on both passes (or neither) and put all pass-specific instruction text in a block AFTER the breakpoint. Ship that assertion as a test against the real API on a small fixture, and add a runtime alarm that logs an error and updates the job's cost projection whenever any pass-2 call after the first returns `cache_read_input_tokens == 0` or `cache_creation_input_tokens > 0`.

**The 1-hour cache write is paid speculatively, before the user commits to generating anything** _(lens: cost-and-failure)_

- problem: Pass 1 writes the document at the 1-hour TTL, costing 2x base input (~$7 on a 700K-token job) rather than 1x uncached. That is a bet on the user approving within the hour. A user who uploads a textbook, reads the proposed plan, decides the topic breakdown is wrong and closes the tab has cost about $7-10 for a plan they threw away, with no way to reclaim it and no cost shown to them beforehand. A user who leaves the approval screen open over dinner comes back to an expired entry, and pass 2 then pays a second full write — 4x base input on the same document.
- fix: Persist `cache_written_at` and render a live 'plan expires in NN min' indicator on the approval screen. If more than ~50 minutes have elapsed at Approve, block and tell the user the document must be re-cached at full price, with the dollar figure, and require confirmation. Because the whole gamble depends on approval latency, instrument it: log time-from-plan-ready-to-approve for every job, and revisit the 1h-vs-5m TTL choice against the measured distribution rather than hardcoding 1h on intuition. Also charge the pre-flight estimate confirmation before pass 1, not just before pass 2, so nobody spends $7 without seeing a number.

**XLSX ingestion is unbounded and can OOM the machine or produce a million-token blob** _(lens: cost-and-failure)_

- problem: A 50MB XLSX is well inside the per-file cap and can hold millions of cells. `openpyxl.load_workbook` in default mode materialises the whole workbook in memory, on a machine that is simultaneously hosting FastAPI, the SQLite worker, and a LibreOffice conversion measured at ~218MB peak RSS. The container OOMs — which from a running job's perspective is indistinguishable from an autostop and kills any concurrent work. If it survives, the resulting Markdown is a multi-million-token blob that either 400s at pass 1 or, worse, slips under a naive gate and costs a fortune to cache.
- fix: Open with `load_workbook(read_only=True, data_only=True)` and stream via `iter_rows`, enforcing hard caps (e.g. 200 rows x 50 columns per sheet, 20 sheets) with explicit truncation markers in the emitted Markdown and a visible UI warning that content was dropped. Run the count_tokens gate on the produced Markdown, never on the source file size. Do the extraction in a child process with an RSS rlimit so a hostile workbook kills the child rather than the worker. Provision at least 2GB with `swap_size_mb` set, since 512MB cannot hold a LibreOffice conversion plus concurrent Anthropic calls holding PDF bytes.

**Image inputs are neither downscaled nor block-counted, so a slide-photo upload 400s or triples cost** _(lens: cost-and-failure)_

- problem: Forty phone photos of lecture slides is a core use case for this app. More than 20 image blocks in a single request triggers a stricter per-image dimension limit and a hard `invalid_request_error` referencing 'many-image requests' — raised after upload, after conversion, after the user has waited. Even under 20 blocks, Opus 5's high-resolution tier bills up to 4,784 visual tokens per image at 2576px versus 1,568 at 1568px, so shipping originals roughly triples the cache-write cost of an image-heavy job for no readability gain on text-bearing slides.
- fix: Downscale every uploaded PNG/JPEG at ingest to a 1568px long edge (2000px absolute maximum) before it reaches count_tokens or the Files API, and persist the downscaled file as the canonical artifact so pass 1 and pass 2 see byte-identical bytes. Batch to keep image-plus-document blocks per request under 20. Keep the later Image Occlusion pipeline separate: it needs its own locally-rasterised, pre-resized copy of the specific diagram page, and the exact image sent to Claude must be the exact image shipped in the .apkg media or the mask geometry is wrong — do not let the two paths share one asset.

**Retention policy fights regeneration, and losing the SQLite DB destroys every user's review history** _(lens: cost-and-failure)_

- problem: Two coupled failures. (a) Keeping 150MB/job of uploads for 30 days on a Fly volume means ~20 retained jobs fill a 3GB volume; auto-extend can only grow, so you pay the high-water mark at $0.15/GB/mo forever. Deleting uploads early instead makes regeneration impossible, which kills the stable-UUID update story that is the whole point of the design. (b) The SQLite DB is the sole record of card UUIDs and their pinned note types. Fly's daily snapshots are explicitly documented as not a backup. If it is lost, every user's next re-import creates duplicate notes and wipes their scheduling — the single worst outcome this design can produce — and every deck must be regenerated at full price.
- fix: Stop storing source bytes on the volume: upload each file to the Anthropic Files API at ingest, persist file_id + sha256 + a frozen deterministic block order in SQLite, and delete the local copy once pass 1 succeeds. Files are free, persist until deleted, and referencing the same file_ids in the same frozen order reproduces a byte-identical cached prefix. Purge the file_ids at the 30-day boundary. For (b), run `VACUUM INTO` a copy and push it offsite on a schedule independent of Fly, and treat the exported .apkg as a secondary recovery source — the GUIDs it contains are the UUIDs, so a lost mapping can be partially rebuilt from a user's own deck. Price regeneration explicitly in the UI as a full cold cache write, and never trigger it automatically.

**'Difficulty' is relative to whatever document you uploaded, so the tag means nothing across decks** _(lens: product-and-ux)_

- problem: Pass 1 rates difficulty per topic with no absolute anchor, so it can only rate relative to the corpus in front of it. Concrete scenario: in June I upload a first-year bio chapter and 'Glycolysis' comes back 'hard' (it is the densest thing in that chapter). In September I upload an MCAT review book and the same topic comes back 'easy' (relative to the rest of that book). Now my collection has diff::hard and diff::easy on the same material, and the tag drives question style too, so the September cards are shallower for no reason I can see. If I build a filtered deck on tag:diff::hard, it is populated by an artefact of which PDF I happened to upload. And because tags are replaced wholesale on update, a regeneration can silently flip a card from hard to easy and quietly empty my filtered deck. There is also a naming collision: Anki/FSRS already computes a per-card difficulty from my actual performance, which is both real and better.
- fix: Replace the free-form rating with a fixed rubric of absolute, behavioural levels baked into the shared system prompt and displayed in the plan editor (e.g. L1 recall a definition, L2 recall a relationship, L3 apply to a given case, L4 multi-step synthesis). Emit the level number as the tag (aianki::l3), rate at the card level rather than the topic level (a topic contains both trivial definitions and hard synthesis), and never re-rate an already-exported card. Do not call it 'difficulty' in the UI — call it depth or level — so it does not read as a competitor to FSRS difficulty.

**Asking the user for a per-topic card count guarantees padded or starved topics** _(lens: product-and-ux)_

- problem: The plan editor asks me to set an integer I have no basis for setting: I have not read the model's density analysis, only a number it guessed. Concrete scenario: the plan proposes 'Krebs Cycle: 12'. The source material contains four genuinely testable facts about it. Pass 2 is told twelve, so it pads: three rephrasings of 'what is the Krebs cycle also known as', a card about who Hans Krebs was, a card asking me to recall that it occurs in the mitochondrial matrix twice. Meanwhile 'Immunology overview: 8' is set against 40 dense pages and drops most of it. I only discover both failures after the four-minute wait, and under the current design I discover them one card at a time during review weeks later.
- fix: Have pass 1 report evidence, not just a number: pages covered and the count of distinct testable claims it found, shown next to the proposal. Replace the raw integer with a coverage setting per topic (essential / thorough / exhaustive) plus an optional hard cap. Instruct pass 2 explicitly that it may return fewer cards than requested and must not pad, and have it report 'generated 6 of 12 — the source did not support more' so the shortfall shows up in the UI as information rather than as filler cards.

**Cloze cards will be well-formed and still be bad, and one specific case corrupts silently** _(lens: product-and-ux)_

- problem: Validating that '{{cN::' exists catches the crash case but not the quality cases a power user will immediately reject. Concrete scenarios: (a) over-clozing — '{{c1::Glycolysis}} converts {{c2::glucose}} to {{c3::pyruvate}}, netting {{c4::2}} ATP' produces four near-identical cards from one fact, and the c4 card is guessable from the surrounding text; (b) whole-clause clozing — '{{c1::Glycolysis is the ten-step cytosolic pathway that converts glucose to pyruvate}}' is a Basic card in a cloze costume and is unanswerable verbatim; (c) the silent corruptor — Anki's cloze syntax is {{cN::answer::hint}}, so any answer text containing a second '::' turns everything after it into a hint that is displayed on the front. A card about a 1::2 stoichiometric ratio, or about Anki's own deck separator, silently gives away part of its own answer, and nothing in the pipeline notices; (d) an answer containing '}}' or '{{' truncates the marker; (e) the escaping order problem — a chemistry deck full of '<' and '>' will either lose text to Anki's HTML rendering or have its cloze markers destroyed, depending on which side of html.escape() the marker insertion happens.
- fix: Write a cloze validator with named rules and run it before the card reaches the review screen: reject or downgrade to Basic if there are more than ~4 ordinals in one note, if any single cloze spans more than about 60% of the field, if fewer than roughly 20 characters of unmasked context remain, or if the answer segment contains '::', '{{' or '}}'. Escape the non-marker segments individually — split the field on the marker regex, html.escape() each plain segment and each answer segment separately, then reassemble — never escape the assembled string. Render the actual front and back in the review UI so the user sees what Anki will show, not the raw markup.

**When the plan is wrong in a way the editor can't express, the only escape is to start over** _(lens: product-and-ux)_

- problem: Rename/delete/count covers a narrow slice of what actually goes wrong with a plan. Concrete scenarios I hit on my first three real jobs: pass 1 names topics after the lecturer's slide titles ('Lecture 7', 'Lecture 8') instead of concepts; it makes 'Cardiac Physiology' one 40-card topic when I want it split three ways; it turns the 12-page bibliography and the course-admin slides into a topic; it ignores the appendix that is actually the most examinable part; my lecturer uses non-standard terminology and I want the cards to use it; the exam is short-answer so I want no cloze at all. None of these are expressible as 'rename this row' or 'change 12 to 8'. My only recourse today is to abandon the job and re-upload, which also re-pays the full cache write, so it is slow and expensive as well as annoying.
- fix: Add a free-text instruction box at both job level and topic level, appended to the pass-2 message after the cache breakpoint — this is free, cache-safe, and is the single highest-leverage control in the whole UI. Add split / merge / add-topic operations where a manually added topic is just a title plus a scope description. Add job-level page-range include/exclude so the bibliography and admin slides can be cut before they cost tokens. Most importantly, add a 'revise plan with this feedback' button that re-runs pass 1 with the user's note appended: the document is still in the 1-hour cache, so this costs one cache read and is the honest escape hatch for everything the structured editor cannot express.

**Four minutes of spinner, and any single topic failure throws all of it away** _(lens: product-and-ux)_

- problem: Between Approve and download there is a long, opaque wait with nothing to look at, and the design has no stated behaviour for its failure and interruption modes. Concrete scenarios: (a) at 90 seconds I cannot tell whether the job is working or wedged, so at three minutes I hit refresh — does the SSE stream reconnect and resume, or have I lost the job? (b) I close the laptop lid; the server-side worker keeps going but my stream dies, and on wake I see an indeterminate state; (c) topic 7 of 15 gets a 429 or returns JSON that fails schema validation, and I get an error page after four minutes with zero cards, having also burned the cache write and 14 successful calls; (d) the developer deploys, which on a single-machine Fly app SIGTERMs the worker mid-job, and my four minutes evaporate. Any one of these once is enough for a friend to stop using the app. Note the earlier wait is just as bad: upload 140MB, convert, count tokens, run pass 1 — that is minutes before I even see a plan.
- fix: Make progress per topic, not per job: a row per topic with queued / generating / done / failed and a live card count, backed by SQLite job state that SSE merely views (client sends Last-Event-ID, server replays from the DB), so refresh and reconnect are invisible and a closed tab is harmless — show a 'you can close this tab, here is the link' line. Stream accepted cards into the review list as each topic lands so there is something to read during the wait. Isolate topic failures: retry with backoff, mark the topic failed, always let the user download the deck built from the topics that succeeded, and offer per-topic retry. Checkpoint per topic so a SIGTERM resumes rather than restarts.

**The app can never remove a card it has already given you, so wrong and retired cards are permanent** _(lens: product-and-ux)_

- problem: An .apkg import can add and update notes; it cannot delete them. Concrete scenario: my first run generates 20 cards under a topic that pass 1 hallucinated from the bibliography. I delete that topic in the plan editor and regenerate. The regenerated file simply does not mention those 20 notes — so they stay in my collection forever, still in review, still wrong. The same happens every time a card must be replaced rather than edited: the design already requires minting a fresh UUID whenever a card flips between Basic and Cloze, which means the old note lives on with stale content alongside its replacement, and I get both in my reviews with no indication which is current. Nothing in the design tells the user this or gives them a way to find the orphans.
- fix: Implement retirement explicitly. When a card is dropped or superseded, re-export that note one final time with its original GUID and note type (which works — same GUID, same notetype, updated fields and tags), tagging it aianki::retired and prefixing the field with a visible marker. On the download page print the exact Anki search (tag:aianki::retired) plus 'select all, delete' instructions, and show the retired count in the pre-download diff. Also state up front, in the UI, that ai-anki can add and update cards but can never delete them — that is a rule users need to know before their first import, not after.

**The obvious power-user cleanup — Change Note Type — permanently and silently breaks all future updates** _(lens: product-and-ux)_

- problem: The deck ships its own notetypes rather than the user's Basic and Cloze. Two things follow. First, cosmetics and workflow: my carefully tuned card CSS does not apply, my saved searches on note:Basic miss every one of these cards, and my Manage Note Types screen gains two entries I did not ask for. Second, the trap: the natural fix a power user reaches for is Notes > Change Note Type to fold them into my real Basic. That changes the notetype id, so on the next regeneration every one of those notes hits the notetype-conflict path — with merge off they are silently dropped (no error, stale content retained, a junk 'Basic+' notetype left behind), and with merge on the import aborts entirely on the cloze/regular mismatch. The user has performed a reasonable cleanup and permanently disabled updates, with no feedback anywhere that connects cause to effect.
- fix: Name the notetypes unambiguously ('ai-anki Basic', 'ai-anki Cloze') so they read as intentional, and ship decent default CSS so users have less reason to touch them. Put a short, prominent 'before you import' note on the download page and in the app: do not change the note type of these cards, and do not edit their fields/templates, or future updates will silently stop working. Add a troubleshooting entry for 'my regenerated deck isn't updating' that names this as the first thing to check, since the symptom (nothing happens) gives no clue on its own.

**A long upload can be rejected wholesale at the end, with a cap the user cannot see coming** _(lens: product-and-ux)_

- problem: The real ceiling is the token count, not the 200-page or 150MB caps, and it is only knowable after upload and after LibreOffice conversion. Concrete scenario: I upload 140MB of image-heavy PPTX over hotel wifi (three minutes), the server converts it, and only then does the token count come back at 1.2M and the job is refused as too large. Five minutes gone, no partial result, and no guidance on what to remove. It is also inconsistent in a way that reads as a bug: 180 pages of text slides went through yesterday, 150 pages of scanned lecture notes fail today, because scanned pages cost several times more. Add the sharp edges from ingestion — a password-protected PPTX, a corrupt DOCX that converts to a blank PDF, a DOCX whose 40 sections render as 80 PDF pages — and 'it didn't work' arrives late and unexplained.
- fix: Validate incrementally as each file arrives rather than at the end: convert and count per file, and show a running page and token estimate in the UI as files are added, with a clear budget bar. When the job is over budget, do not reject it — let the user deselect files or exclude page ranges to get back under, without re-uploading. Name the offending file in every error ('we couldn't read lecture4.pptx — it looks password-protected'), detect encrypted Office files up front, and reject PDFs that convert to visibly empty pages before they cost a single Claude token.

**No defined behaviour when some pass-2 topic calls fail** _(lens: completeness)_

- problem: Pass 2 is a fan-out of 4-6 concurrent calls over N topics with no stated failure policy. Real failures are routine: 429 from ITPM limits during the fan-out, 529 overloaded, a stream that drops mid-response, a structured-output response that parses but contains zero usable cards, or a topic whose max_tokens is exhausted by thinking. Scenario: 12 of 15 topics succeed, 3 fail with 429. Undefined: is there a retry, how many, with what backoff, and does a retry re-read the cache or pay a fresh write; is the deck downloadable with 12 topics; are the 3 failed topics marked so a later regeneration fills them without minting new UUIDs for the 12 good ones; does the job end as `complete` or `failed`. An implementer will pick `asyncio.gather` and get whole-job abort on the first exception.
- fix: Define per-topic outcomes independent of job outcome: each topic row gets succeeded/failed/retrying with an attempt count. Retry policy: 3 attempts, exponential backoff with jitter, respecting `retry-after` on 429; use `return_exceptions=True` semantics, never whole-job abort. A job with ≥1 successful topic is downloadable and labelled 'partial (12 of 15 topics)'. Failed topics stay retryable in place, which also requires the per-slot UUID rule above so a retry does not renumber the successful topics.

**Prompt-cache viability rests on an unverified interaction with structured outputs, and the required request layout is not part of the design** _(lens: completeness)_

- problem: The entire cost model — one 1-hour cache write, then $0.50/MTok reads for every topic — depends on pass 1 and pass 2 sharing a byte-identical prefix. Two things block that today. First, the caching verification explicitly flags as UNVERIFIED whether `output_config.format` is rendered into the cached prefix; pass 1 needs a deck-plan schema and pass 2 needs a different card schema, so if the schema is part of the key, every pass-2 call misses and a 15-topic job costs roughly $30 more than budgeted, with no error raised. Second, the design has not adopted the request layout the verification says is required: one pass-agnostic system prompt, documents in messages with the breakpoint on the last document block, pass-specific instructions after the breakpoint, and identical `effort` and thinking config across both passes. The natural implementation — a 'deck planner' system prompt and a 'card writer' system prompt — silently destroys the cache.
- fix: Run the measurement before committing to the architecture: pass 1 with output_config.format, pass 2 with a different schema, assert `cache_read_input_tokens > 0` on pass 2. If it is zero, either use no structured outputs on either pass (strict tool call instead) or accept the cost. Then freeze the layout in a single shared request-builder function with the system prompt, effort, thinking config, tools and tool_choice as module constants used by both passes, and add an integration assertion that pass-2 calls 2..N have cache_read>0 and cache_creation==0. Also decide the fan-out priming step explicitly — fire one topic call, await its response start, then fan out the rest — since concurrent cold calls each pay the 2x write.

**The 200-page cap is unenforceable as written and is not the binding constraint** _(lens: completeness)_

- problem: Two verification findings collide with the agreed cap. DOCX has no intrinsic page count until laid out (a 40-section DOCX rendered to 80 PDF pages), so 200 pages cannot be checked at upload time — only after LibreOffice has already spent 30-60s converting. And the real ceiling is the 1M-token context window: 200 pages at 1,500-3,000 text tokens plus up to 4,784 visual tokens each is 600K-1.5M tokens, so the upper half of the allowed range does not fit and pass 1 fails with a context error after the user has uploaded 150MB and waited through conversion. There is no defined admission-control behaviour, no defined message to the user, and no defined partial outcome when one file of five blows the budget.
- fix: Move admission control to tokens, not pages: after conversion, assemble the document blocks and call `client.messages.count_tokens()`; reject above a stated ceiling (~700K, leaving room for output) with a message naming the offending files and the measured size. Keep the page cap as a cheap pre-filter only for native PDFs. Define the partial path: either reject the whole job or let the user deselect files and re-check. Show the token count and an estimated cost before the user confirms pass 1.

**Every user shares one identity, so every user can read every other user's documents and decks** _(lens: completeness)_

- problem: One shared password means the session cookie carries no user identity. There is no stated ownership model on jobs, uploads, or generated decks, and no stated authorization rule on the download and job-status endpoints beyond 'is logged in'. Scenario: friend A uploads a private set of clinical notes; friend B, legitimately logged in, opens the job list (or guesses/enumerates a sequential job id) and downloads them along with the .apkg. This may be an acceptable trade for a handful of friends, but it has not been decided, and it determines whether the UI has a job list at all, whether job ids are UUIDs or integers, and what the app tells users about privacy.
- fix: Make it an explicit decision and implement to it. Minimum: job/file ids are random UUIDs, never sequential; the job list either shows only the current browser's jobs (tracked by a per-browser id in the session row) or is documented as shared. State the retention and visibility model on the upload page so friends know their documents are readable by everyone with the password. If isolation is actually wanted, the shared-password scheme is the wrong primitive and needs per-user passwords.

**The SQLite schema and the concurrency model of the single process are both undefined** _(lens: completeness)_

- problem: No tables, columns, or indexes are specified, and — more dangerous — nothing says how an async FastAPI app and an in-process background worker share one SQLite file on a 1-vCPU machine. Scenario: two friends submit jobs at once. Undefined: whether jobs run concurrently or serially; whether the worker is an asyncio task, a thread, or a pool; whether blocking sqlite3 calls run on the event loop (they will, by default, and will stall the SSE streams during LibreOffice-adjacent bursts); whether WAL is enabled; what `busy_timeout` is; whether writes are serialized behind a single writer. Separately, the genanki finding that built-in Models are mutable module-level singletons mutated by `to_json` means two simultaneous .apkg assemblies touch shared state, and the recommended assembly lock is not in the design.
- fix: Write the schema down (jobs, files, topics, cards, sessions, usage) with the deck-lineage entity from the first issue. Specify: WAL mode, `busy_timeout=5000`, `foreign_keys=ON`, a single writer path, and all DB access via `run_in_executor`/`asyncio.to_thread` or aiosqlite so the event loop never blocks. Specify the job concurrency limit (start at 1 concurrent job on shared-cpu-1x), and three independent semaphores that are not conflated: LibreOffice (sized to vCPUs, =1 on 1 vCPU), Claude fan-out (4-6), and a mutex around genanki Package assembly.

**Upload handling has no defined validation, and the inputs are attacker-controlled archives fed to LibreOffice** _(lens: completeness)_

- problem: DOCX, PPTX and XLSX are zip archives, and the design routes them straight into headless LibreOffice and openpyxl with no stated validation. Undefined behaviour for: a decompression bomb (a 2MB XLSX expanding to gigabytes through openpyxl on a 2GB machine — OOM kills the machine and every in-flight job); a password-protected DOCX, which the verification names as the realistic way to hang LibreOffice with no prompt available; a file whose declared extension does not match its content; a filename containing path separators or `..` used to build a storage path; and a 0-byte or text-renamed-to-.docx file that converts 'successfully' into a blank PDF and then burns real Opus tokens. There is also no stated storage layout for uploads on the volume, and no statement that TMPDIR must be on the volume rather than the 2000-IOPS ephemeral rootfs.
- fix: Define an ingest gate: sniff content type with libmagic and reject on mismatch; detect encryption with msoffcrypto-tool up front and return a clean error; cap uncompressed zip size and entry count before handing to openpyxl/LibreOffice; never use the client filename for any path (store under `{volume}/uploads/{job_uuid}/{file_uuid}` and keep the original name as a DB column only); enforce the 50MB/file and 150MB/job caps while streaming, not after buffering. Post-conversion, verify the PDF exists, is non-zero, and has extractable text or images before it enters the Claude pipeline — never branch on soffice's return code, which is unreliable in both directions.

**No cost estimate, no per-job budget, and no way to cancel a running job** _(lens: completeness)_

- problem: The verification's own cost model puts a 200-page job at roughly $17.50 of input alone before thinking and output, on a key shared by everyone who has the password. There is no defined pre-flight estimate, no per-job token or dollar ceiling, no global monthly cap, and no cancel control. Scenario: a friend uploads a 180-page textbook, approves a 25-topic plan by mistake, and there is no button that stops it — the job runs to completion and spends $40. Second scenario: a runaway or malicious loop submits jobs overnight and the first signal is the Anthropic bill.
- fix: Show a token count and a dollar estimate on the plan-approval screen, computed from count_tokens plus the approved card counts, and require confirmation above a threshold. Add a `cancel` job state checked between topic calls and before each API call, wired to a visible Cancel button. Persist `cache_read_input_tokens`, `cache_creation_input_tokens`, `input_tokens`, and output tokens per call in SQLite; enforce a rolling 30-day spend cap that refuses new jobs, and expose the running total in the UI.

**SSE is named as the transport but has no event contract, heartbeat, or reconnect semantics** _(lens: completeness)_

- problem: 'Server-Sent Events for progress' is the whole specification. Undefined: the event schema and event names; whether the stream is the source of truth or a view over SQLite; what happens when the user closes the tab mid-job (job continues? worker tied to the request?); what a reconnecting client sees for the progress it missed; how long the stream stays open with nothing to report. Concretely, a pass-2 topic call can run well past 60s with no output, and the Fly verification found that without `Content-Encoding: none` the proxy buffers the compressed response and events arrive in multi-second batches — so the progress bar looks frozen and the user resubmits.
- fix: Define SSE as a strictly read-only view over job state in SQLite: the worker writes progress rows, the endpoint tails them. Assign monotonic event ids per job, honour `Last-Event-ID` by replaying from the DB, and emit a `: ping` comment every 15s. Set `Content-Encoding: none`, `Cache-Control: no-cache`, `X-Accel-Buffering: no` on the response and `[http_service.http_options] idle_timeout = 600` in fly.toml. Specify the event set (topic_started, topic_done, topic_failed, job_state, cost_update) and that closing the tab never affects the worker. Use `type = "requests"` concurrency and reap dead streams.

**Image Occlusion needs a second, incompatible ingestion pipeline that the agreed ingestion decision forecloses** _(lens: completeness)_

- problem: The design commits to sending PDFs to Claude as native document blocks and treats Image Occlusion as a later phase of the same system. Anthropic's own documentation states that for PDFs, pages are rasterized server-side at dimensions you do not control, so returned coordinates cannot be mapped back onto the page. Occlusion masks are normalized against the exact image shipped in the .apkg media. So the agreed ingestion path cannot produce usable mask geometry at all — the later phase is not a feature toggle on top of this pipeline, it is a parallel pipeline (local rasterization with pypdfium2/PyMuPDF, optional figure crop, pre-resize to the high-res tier, image blocks, and shipping that exact PNG as media). Planning it as 'a later phase' understates the work and risks a data model that has nowhere to put a rasterized page asset.
- fix: Either declare Image Occlusion out of scope for v1 and note the pipeline split as a known architectural cost, or reserve for it now: a `media_assets` table keyed by content hash (the verification found genanki keys media by basename, so same-named figures from different PDFs silently clobber each other), a per-card link to its asset, and a note that occlusion cards use a third pinned model_id for a genanki Model subclass emitting `originalStockKind: 6` with per-field `tag` values. Also record that the imported IO notetype will always land as a duplicate in the user's collection and should be named 'Image Occlusion (ai-anki)' deliberately.

**Nothing defines how the top-level deck is named or what happens when two jobs pick the same name** _(lens: completeness)_

- problem: Anki matches decks by name, not id. The design never says who names the root deck — the user, the first uploaded filename, or the LLM's pass-1 output. Scenario: a user generates two separate decks from two different courses and both pass-1 runs propose a root named 'Biology'. On import the second job's subdecks graft into the first job's tree, and any card UUID collision or topic-path collision silently merges two unrelated study sets. There is likewise no stated .apkg filename convention, and no stated rule for what the user sees before download.
- fix: Make the root deck name an explicit, required, user-editable field on the job, defaulted from the first filename, validated for '::' and empty components, and persisted on the deck lineage so regenerations reuse it verbatim. Show the full deck tree that will be created on the download page. Name the .apkg from the root deck plus job short id. Also apply the sanitization rules the verification found: strip '::' from each component, reject empty components, clamp tree depth below Anki's 11-level limit, and assert deck ids are unique and never 1.

**No dedup rule for the same fact generated under two topics** _(lens: completeness)_

- problem: Pass 2 runs per topic in parallel with the full document in every call, so overlapping topics will generate the same fact twice — this is a predictable consequence of the chosen architecture, not an edge case. The verification confirmed Anki's apkg importer matches only on GUID and does no first-field dedup, so both notes import cleanly and Anki's browser later flags them as duplicates for the user to clean up by hand. The design contains no dedup step and no defined behaviour when duplicates are detected.
- fix: Add an explicit post-pass-2, pre-UUID-assignment dedup stage and specify its rule: normalize the front field (strip HTML, lowercase, collapse whitespace) and drop exact matches; optionally flag near-duplicates for review in the plan UI rather than deleting silently. Record which topic won, since the surviving card's deck path is then frozen. If dedup is deliberately skipped for v1, say so and tell users on the download page to run Anki's Find Duplicates.

**SQLite has no backup plan, and losing it is the most destructive failure in the system** _(lens: completeness)_

- problem: Fly's documentation states plainly that daily volume snapshots are not a backup. The SQLite file holds the card UUID ledger; if it is lost, every user's next regeneration duplicates their entire deck and orphans all their review history, permanently and irrecoverably. The design mentions a persistent volume and nothing else — no backup cadence, no offsite target, no restore procedure, and no test that a restore works.
- fix: Specify a backup job: `VACUUM INTO` a copy on a schedule (hourly is cheap at this size) and push it to object storage with a retention window, running inside the same process on a timer since Fly release_command machines cannot mount the volume. Document the restore procedure. Also configure volume auto-extend (`auto_extend_size_threshold` plus both `auto_extend_size_increment` and `auto_extend_size_limit`, since Fly warns that omitting either disables it) and note that purging source files early is the real disk defence.

### MINOR

**Deck-name sanitization can collapse two distinct topics into one deck, silently merging their cards** _(lens: correctness)_

- problem: Deck ids are keyed by path and written via `decks.update({str(deck_id): ...})` — two Deck objects sharing an id means the last name wins and ALL notes from both land in one deck, with no error. Sanitization creates the collision: stripping '::' from topic names maps sibling topics "A::B Overview" and "AB Overview" to the same path, as does trailing-whitespace stripping on "Glycolysis" vs "Glycolysis " — both plausible LLM outputs in one plan. If the id is derived as a hash of the sanitized path, the two decks collide and one topic's cards vanish into the other. Separately, deck_id 1 collides with Anki's Default deck and silently swallows the cards (verified), and an empty path component is renamed by Anki to the literal string "blank".
- fix: Sanitize first (strip '::', strip whitespace, reject empty components, clamp depth), then assert uniqueness of the resulting full paths across the whole plan and fail loudly with a user-facing message if two topics collide — do not auto-suffix silently. Derive deck_id deterministically from the sanitized path (e.g. uuid5 mod 1<<31), assert `deck_id != 1`, and assert all deck_ids in a Package are distinct before writing.

**Document block order and source form must be frozen at job creation or a resumed job misses the cache entirely** _(lens: correctness)_

- problem: The cache key is a byte hash of everything up to the breakpoint, and the lookback only checks 20 positions. Trigger: a job is killed by a Fly deploy mid-fan-out (guaranteed, since a single-machine volume app gets rolling deploys that stop the only machine, and kill_timeout caps at 300s). The worker restarts and re-reads the uploads from the volume in `os.listdir` order rather than the upload order used by pass 1. The block sequence differs, the prefix hash differs, and every resumed pass-2 call pays a full uncached read plus a write on ~700K tokens. The same happens if pass 1 inlines base64 while the resumed pass 2 references file_ids — which is likely, since 50MB files cannot be inlined at all under the 32MB request limit.
- fix: Freeze the exact block manifest in SQLite at job creation: ordered list of stable file IDs, the chosen source form (file_id vs base64), and the media types — and rebuild pass-2 requests only from that manifest, sorted by stable ID. Standardize on the Files API (`files-api-2025-04-14`) for all documents so the form never varies with file size. Route .txt/.md through `text/plain` document blocks so they sit inside the same cached prefix rather than as separate text blocks.

**Duplicate job submission and SSE reconnects can double the bill** _(lens: cost-and-failure)_

- problem: A double-clicked Generate button, an impatient user reloading during the slow pass-1 call, or an SSE reconnect wired to anything that starts work, creates two jobs over the same uploads. Both run pass 1, both write the document cache, the bill doubles, and the user is shown two competing plans. Because a pass-2 topic call can run 60s+ with nothing to report, a missing SSE heartbeat also makes the UI look dead and invites exactly this re-triggering.
- fix: Derive a job idempotency key from (session id, sorted list of file sha256s) and enforce it with a UNIQUE index; POST /jobs returns the existing job on collision rather than creating a second. Disable the button on submit. Make SSE a strictly read-only GET view over job state in SQLite with `Last-Event-ID` replay, never a trigger for work, and emit a `: ping` comment every 15-20s. Set `Content-Encoding: none` on the SSE response (Fly's proxy buffers before compressing, which visibly breaks streaming) and `idle_timeout = 600` in `[http_service.http_options]`.

**The root deck name is permanent, and the user never gets asked what it should be** _(lens: product-and-ux)_

- problem: Deck placement is write-once, so whatever the first export names the top-level deck is where these cards live for good. Concrete scenario: the app defaults to the uploaded filename and my cards land under 'BIOL2040_lecture_notes_final_v3::...' at the top level of a deck tree I have curated for three years. I can rename it in Anki, which does move the cards, but then every future regeneration recreates the original name as an empty deck next to it, because the package still names the old path. There is no point in the flow where I am asked.
- fix: Ask for the root deck name in the plan editor, before the first export, with the full preview path shown ('Med School::Physiology::Glycolysis'). Validate it: strip '::' from user-entered components, reject empty components, clamp total nesting to well under Anki's 11-level limit. Label it as permanent, and after the first export lock it together with the rest of the deck path.

**The source-page tag looks authoritative and is not** _(lens: product-and-ux)_

- problem: Citations cannot be combined with structured outputs, and scanned PDFs are not citable at all, so any page number is self-reported by the model and unverifiable. Concrete scenario: a card gives an answer I doubt, I see tag page::47, I open the PDF to page 47 and it is about something else — or worse, the job had three source files and the tag does not say which. The first time a page reference is wrong I stop trusting every other page reference, and by extension the cards. This is a small feature that does active damage to trust.
- fix: Make the tag self-describing and file-qualified (src::lecture4_pdf::p47), label it in the UI as an approximate model-reported location rather than a citation, and suppress it entirely for scanned/image-only sources where the model has no text anchor at all. If it cannot be made reliable enough to be worth clicking, drop it — an absent reference is better than a wrong one.

**One shared password means no per-user accounting for a bill that scales with other people's uploads** _(lens: product-and-ux)_

- problem: Auth is a single shared password, so every friend is the same user and there is no identity to attribute spend to. Concrete scenario: a friend uploads a 900-page pharmacology text, gets told it is over the cap, splits it into five jobs, and runs them all — several hundred thousand tokens of cache writes plus opus-rate output, on the developer's card, with no per-job cost shown to them and no ceiling. From the friend's side this is completely invisible; they think they are pressing a free button. From the developer's side the first signal is the monthly invoice.
- fix: Show an estimated cost next to the plan before Approve, in plain money, so the person pressing the button sees what it costs. Enforce a global daily token budget in SQLite with a clear 'daily limit reached, try tomorrow' message rather than a failure, and add a kill switch. If per-user accounting matters later, the cheapest upgrade is a per-person password or invite code rather than one shared secret, which also lets you rate-limit the one friend who discovers the app is fun.

**Schema migrations have no home — release_command machines do not mount the volume** _(lens: completeness)_

- problem: Fly documents that volumes are not mounted to the temporary machine created for `release_command`, and are unavailable at build time. The conventional place to run migrations is therefore unavailable, and the design does not say where they run or what tool manages them. Scenario: a deploy adds a column, the app starts, FastAPI begins accepting traffic, and the first request hits a table that has not been migrated yet.
- fix: Run migrations in a startup step that completes before the server binds/accepts traffic (FastAPI lifespan, before yield), guarded by a lock so a restart mid-migration is safe. Pick a tool (Alembic, or hand-rolled `PRAGMA user_version` steps — either is fine at this size) and commit to it now, because retrofitting migration history onto a live UUID ledger is painful.

**Export timestamp monotonicity is required for updates to land and is easy to get wrong** _(lens: completeness)_

- problem: Anki's default update condition is IF_NEWER and genanki writes note `mod` at 1-second resolution from the package timestamp. Two consequences with no defined behaviour: regenerating and re-exporting within the same second produces an .apkg whose updates Anki silently discards (verified in the research — the field stayed at v1), and a user who edits a note in Anki makes it newer than the app's export until the next export, so whoever wrote last wins. The design says nothing about which side should win or about guaranteeing an increasing timestamp.
- fix: Persist `last_export_ts` per deck lineage and pass `Package.write_to_file(timestamp=max(now, last_export_ts + 1))`; never pass a fixed timestamp for reproducible builds. Pick and state the conflict policy — 'regeneration overwrites your manual edits to these cards' is the honest default — and put it on the download page alongside the note that tags (including `marked` and `leech`) are replaced wholesale on every update, and that a minimum Anki version of 23.10+ is required.

**Model-generated HTML is escaped for Anki fields but nothing is said about the app's own preview UI** _(lens: completeness)_

- problem: The verification correctly requires `html.escape()` on LLM-produced fields before they go into Anki (and correctly warns not to escape cloze markup or injected img tags). But the plan-approval and card-review screens render the same model output in the React app, and no escaping/sanitization rule is stated there. Since document content is attacker-influenced — a shared-password app where any friend can upload a file containing instructions or markup — model output reaching `dangerouslySetInnerHTML` or an unsanitized preview is a stored-XSS path against everyone else using the app. Filenames echoed into the UI have the same problem.
- fix: State the rule at both boundaries: the API returns card text as plain data and the frontend renders it as text (never dangerouslySetInnerHTML) except for a deliberately sanitized preview that whitelists the small tag set Anki cards actually use. Escape filenames on display. Add a Content-Security-Policy header on the SPA. Also decide the escaping order once, in one function: escape first, then insert cloze markers and img tags, never the reverse.
